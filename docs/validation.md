## 参考纠偏后的结构与语义验证计划

本节是待实施的验证要求，来源与设计前提见[纠偏计划](reference-correction-plan.md)，不是新增测试通过报告。参考[书中第 7 章](../references/aidlc-book-reference/aidlc-book-baojun/book/chapters/ch07-verification.md)区分确定性检查、独立测试、模型审查与人工判断，按变更风险选择强度；不能把上游实验标为 VERIFIED 当作 AgentHub 已验证。

| 验证对象 | 后续应验证的行为 | 不能据此推断的结论 |
| --- | --- | --- |
| 数据合同 | 拒绝缺失字段、错误类型、无效版本和不满足条件的输入；需求包含适用的质量与边界约束 | Schema 完整不证明需求符合真实意图 |
| 追溯关系 | 拒绝重复 ID、未知引用、孤立 Story、空验收；检查需求覆盖、依赖环与版本适用性 | 引用存在不证明语义一致；覆盖率不等于交付成功率 |
| Markdown 与结构化记录 | 原文可追溯，正式记录与投影版本一致，重新生成不改写原意 | 摘要流畅或导出成功不证明已批准 |
| 关键变更 | 需求、验收、Standards 或 Intent 的变化显示影响和差异；旧版本批准不得静默覆盖新内容 | 候选数据或工具自填标记不能产生人端审批 |
| 执行与验收 | Bolt 的阶段和证据适用于具体执行与交付版本；独立场景检查预期与结果 | 测试、模型审查、CI 和 Run 完成均不代替用户最终验收 |

可参考上游 EXP-03-01 的五类失败夹具和 EXP-03-02 的依赖图校验，但应由 AgentHub 的字段、实际用例与权限规则决定测试。上游对非功能需求的演示门槛不直接复制成所有项目的固定数量要求。模型审查若后续接入，只提供待核实意见，不生成可信验收结论。

既有 B1–B3 的类型、行为、浏览器及人工反馈证据继续适用于原覆盖范围；它们没有覆盖本节尚未实现的数据模型。本轮仅修正文档及引用，不运行上游实验、不新增 Schema / 迁移，也不替代 X1–X5 或产品准入。

## 理解与决策闭环的验证要求

本节依据用户于 2026-10-25 明确确认的[先理解再推进](governance.md#先理解再推进)制定待实施的产品验证要求，不是已经通过的测试或人工验收。

| 场景 | 应观察的行为 | 判断边界 |
| --- | --- | --- |
| 核心机制尚未理解 | 用户可继续追问并获得业务与技术解释，尚未解决的问题保留，不推进依赖该判断的正式实现 | 是否理解由用户判断；不能由模型打分、自动填确认或因用户沉默而推定 |
| 有多个可行方案 | 呈现影响范围、各方案收益风险、推荐依据、关键假设与未知项，并可追溯用户选择 | 只有推荐结论或规范文案不足以证明理解与选择成立 |
| 需要参考资料或实验 | 资料对应具体知识缺口并标明适用性；实验区分问题、预期、方法、实际观察和未验证项 | 链接存在不等于已读懂；未执行实验不能写成已验证；实验须在授权范围内 |
| 决定后内容发生变化 | 用户能看到变化及影响，原决定绑定的内容和版本保留；按既有规则重新核对 | 旧决定不能静默替新方案背书，也不能扩大执行权限 |
| 首版未接 Runtime | 外部讨论、实际实验记录与 Hub 自有观察标明来源，未决定 / 未执行 / 未验证保持明确 | Hub 不能仅凭待决定状态宣称能阻止外部 Agent |
| 实际结果与原意图不符 | 依据具体场景和交付版本记录偏差，返回修复或商讨意图变更 | 不能更改原目标来迎合结果；CI、报告与人工实际验收分别判断 |

用户最新将记录体系与 Harness 建设前置；上述理解 / 决策要求保留为后续 LLM 接入后的产品验证目标，不要求先完成成熟的决策走读界面。届时可观察材料是否帮助用户解释“为什么做、业务与技术机制怎样成立、如何检验”，允许自愿复述或追问，不强制知识测验。自动检查只覆盖结构、引用、版本、权限和可重复的系统行为；实际理解、关键选择与最终验收仍分别由用户判断和确认。首次样例走读不证明长期稳定性改善。

## 当前 MVP 目标与 E1–E4

本轮产品意图回顾明确：先通过对话澄清意图、责任、边界和验证方式，由用户确认 Intent；人理解方案理由、收益和风险后，再按交付单元推进；Issue 和 PR / Review 应展示 What、Why 与可验证的 Result。较大的 Intent 可以用父 Issue 表达，子单元对应子 Issue，拆分依据源头问题和交付边界。

当前先建设 Markdown + JSON Schema 记录体系与最小 Harness，再接入云端模型验证解释、审查和执行链路；分状态看板按结构化合同投影。保留单主要写入 Run，基础不依赖先完成成熟审阅 UI。既有 DeepSeek Loop 是技术起点，本轮未重新指定具体模型或服务商。本地小模型后续可用于辅助 Review 或文档总结；已有 Agent 的适配后置，须另行验证运行时约束。

初始化时的技术验证切片仍可用于一个真实、可复现的小型本地代码缺陷修复：

Issue → 人工批准 Grant → 单主要写入 Run → Hub 自有 DeepSeek Loop → 受控调查、修改和真实测试 → Trusted Git Broker 本地 Commit → Evidence → 绑定 Commit 的 Review。

该切片不再被视为单独足以证明完整产品目标。Hub 负责提交前检查和本地测试，通过后在获准范围内提交、推送并查看 CI 信息；用户介入最终实际运行验收。已确认先行看板交付及 PR 四段式说明；具体布局、PR 创建方式和完整运行验收场景仍待细化，完整产品 MVP 边界尚未重新冻结。产品责任明确不构成实际远程操作授权或能力验证。

| 验收项 | 必须证明的结果 |
| --- | --- |
| E1：真实研发交付 | 问题可复现或有明确验收场景；已确认 Intent、派生 Issue、确定版本、提交前检查、本地测试、CI / 运行结果及 PR / Review 影响说明相互对应，并经用户介入实际运行验收。技术切片只能证明其覆盖部分 |
| E2：越权操作阻断 | 超出 Grant 或已验证能力的操作被实际阻断，不能仅以模型承诺为证 |
| E3：权威事实与审批保护 | 不可信指令不能篡改 Intent、其修改授权、正式领域事实、人工审批与可信验收；不能通过擅改目标或验收条件消除实现偏差 |
| E4：中断与安全恢复 | 能识别中断、未知副作用并依据实际状态受限恢复，不能用请求记录代替执行事实 |

Codex 正式适配、完整 MCP、多 Agent、多项目调度、Electron 打包、通用 VM 管理平台、完整 Dashboard、通用 Skill / Workflow 市场仍延期。本地辅助模型不是第一版必要条件。Issue 看板与执行看板结合是产品目标，首版最小呈现和交互范围待确认。

## 看板版本与后续 Runtime 的验证边界

用户已确认先交付 Intent / Issue 看板，先与外部 Agent 反向对话并记录结论，之后再接入 Runtime。两个交付层次分别验证，不能要求先完成全部运行能力才开始看板，也不能把看板可用等同于运行控制已验证。

| 交付层次 | 需要验证的结果 | 不从该层推导的能力 |
| --- | --- | --- |
| 看板版本 | 项目 Intent / Issue 关联清楚；支持理解影响、方案取舍及业务与技术核心逻辑，记录外部解释、资料、追问、必要实验与用户决定；未理解、未决定、未执行和未验证清楚区分 | 未执行的工具、CI、Git 操作不显示为完成；不证明 Sandbox、可信审批隔离或 Agent 执行能力 |
| 后续真实 Runtime | 依据 C01–C08、E1–E4 和对应准入，验证执行、检查、交付及人工实际验收 | 看板字段、手工记录、对话或截图不能代替真实执行与版本证据 |

看板已确认采用 CLI 或其他工具写入、用户检查与审批；关键内容审批与普通记录在边界内直接保存的原则已确认；边界划定方式、协议、命令、布局、存储和附件入口尚未冻结。PR 四段式是已确认的交付说明要求，不意味着首个看板版本必须实现远程 PR 创建器或附件上传。人工截图等证据由用户提供，仍需说明适用场景与版本。

## 阶段一设计检查与后续真实项目验证

2026-10-23 用户明确阶段一可基于既有 Intent 开始，真实项目后续导入验证。本阶段已形成[可评阅材料](phase-1-review.md)；产品交付是[首版闭环与最小交互草案](architecture.md#阶段一首版交互草案2026-10-23)、候选能力范围、待决定事项及验收方向；不以用户先提供真实项目或任务为开工条件。

阶段一通过文档评阅和场景走读检查以下设计要求。表中列出预期行为，没有执行结果，也不构成产品测试或技术 Pass：

| 走读情况 | 设计应如何处理 |
| --- | --- |
| 意图尚有关键歧义或未经用户确认 | 继续澄清并明确展示草案及未决事项，不把候选内容当作正式意图进入执行 |
| 拟拆分的子 Issue 与源头问题没有独立交付理由 | 说明或调整边界，不为填满流程而继续拆分 |
| 执行中需要改变意图或降低验收条件 | 展示原因、影响和变更提案，先商讨并获得明确授权 |
| 提交前本地测试失败或结果未知 | 留存真实状态并修复或核查，不能视为本地检查通过后提交推送 |
| 推送后 CI 失败 | 关联目标版本，在原意图、预算和授权内返工；新的交付版本重新判断证据适用性 |
| Issue / PR 说明一致，但实际行为偏离 Intent | 人工实际验收应识别偏差并退回，不能仅凭文本一致或 CI 通过判定完成 |
| 中断后文件、进程或提交结果不明 | 核查副作用和当前授权，不假定成功、回滚或可以直接重试 |

阶段一完成需要用户评阅并确认首版范围、必要交互与重要取舍。尚未决定的布局和 PR 创建方式应列为待决定事项，不自动升级为已确认设计；设计确认不替代实现准入。

后续能力就绪并取得相应授权后，再导入真实项目或任务，采集本地测试、CI、运行观察和人工验收依据，检查 E1–E4 及产品有效性。真实项目验证的场景、比较基线和评价方法应在执行前明确，场景走读或模拟结果不能证明实际推进稳定性和可理解性已经改善。工程侧 X1–X5 和技术准入仍按后文处理。

V12、V13、V15 与 V16 适用于先行看板的工具写入和记录流程，V14 对应已确认的 PR 表达要求；V01–V11 保留完整闭环场景，只有其涉及的真实能力接入后才可运行验证。以下场景是未来验证预期，**不是已执行的自动化测试**。示例数据来自[虚构标题筛选任务](architecture.md#贯穿示例标题筛选修复)，不能成为 AgentHub 的新增业务目标。

| 场景 | Given：前提 | When：触发 | Then：可观察预期 |
| --- | --- | --- | --- |
| V01 已有确认与关键缺口 | 已有适用的已确认 Intent，某交付条件仍不明 | 开始对话或恢复上下文 | 复用已有确认，只说明并澄清影响本次判断的缺口；方案显示理由、收益和风险 |
| V02 草案与执行授权 | 只有候选 Intent，或已有确认但未批准 Grant | 模型提出工具动作，或用户只点击确认 Intent | 草案不变成正式意图；仅确认 Intent 不放行执行。信息足够、用户另行批准有效 Grant 且能力已验证后，才进入相应执行 |
| V03 意图变更 | 已确认示例要求关键词命中两个标题 | 实现困难，建议改为只保留未完成事项 | 显示变更理由、差异及影响；未经商讨授权，原 Intent 保持规范效力 |
| V04 合理拆分 | 一个筛选修复可独立验证 | 生成 Issue 方案 | 用一个交付单元承载，并解释边界；普通实施操作不被机械拆成多个交付 Issue |
| V05 授权与能力 | Grant 仅允许某工作范围，或执行能力尚未验证 | 提出越界动作，或试图开放未验证能力 | 受影响动作不执行，说明限制及后续判断需要；有效授权且能力已验证的合法动作才可实际推进 |
| V06 建议与执行事实 | 模型声称工具已执行，但尚无观察；或只有部分观察 | 更新进度 / 交付说明 | 标为建议、待执行或部分 / 未知；真实观察存在时展示实际结果及来源，不补造成功 |
| V07 本地检查 | 适用检查失败、工具不可用或结果未知 | 准备提交推送 | 不进入“本地检查已通过”的交付分支；保留原因并修复或核查。真正通过且授权 / 能力适用后才交付 |
| V08 CI 与版本 | 示例版本 A 的 CI 失败，修复得到 B | 准备 B 的交付材料，或 CI 暂不可获取 | 关联 B 的真实远端事实；重查证据适用性，不把 A 的检查或暂不可获取记录成 B 已通过 |
| V09 语义与人工验收 | 示例 CI 通过，但筛选额外隐藏已完成事项 | 人工输入“登录”，再清空关键词 | 对照原意图应命中前两条、清空后显示三条且数据未变；偏差退回修复，CI 不代替接受。版本与观察齐备后由用户决定 |
| V10 中断与恢复 | 已请求取消，或提交 / 工具结果中断不明 | 展示停止结果或尝试恢复 | 分别说明请求、已知停止与未知副作用，先核查再判断是否可恢复；不假定回滚或盲目重试 |
| V11 保存与过期视图 | 保存失败、重复确认请求，或当前记录已变化 | 提交确认、修改或验收 | 明确失败并保留输入，不产生虚假确认或重复记录；旧视图的决定不能静默覆盖新版本 |
| V12 看板先行 | 尚未接入模型或执行 Runtime | 用户查看项目概览、关联 Intent / Issue 并记录外部讨论结论 | 能看清问题、方案依据、用户决定与验证计划；未接入的执行、检查和交付不冒充已完成 |
| V13 方案反向对话 | Issue 有候选解决方案，尚无用户方案决定 | 外部 Agent 与用户讨论为什么、收益、风险和验证方式，随后录入 Hub | 记录讨论结论及用户最终选择；仅有 Agent 建议时保持待决定，不因录入摘要自动认定已批准 |
| V14 PR 表达与截图 | 准备说明某次实际修改，部分验证可能尚未完成 | 按模板组织 PR 文本并由用户补充截图等证据 | 包含做了什么、为什么这么做、如何验证、结果怎么样；结果与场景 / 版本对应，未验证保持未验证，不推导自动创建 PR 权限 |
| V15 工具写入与审批 | 已划定本次写入边界，Agent 提交普通记录、关键变更或边界外请求 | 调用写入工具并查看记录或审批信息 | 边界内允许的普通记录带来源保存；关键变更即使在边界内仍待用户判断；边界外不直接改正式记录。写入成功不显示为人工批准，边界不明时先澄清 |
| V16 新增子 Issue | 用户已确认 Intent 及交付清单，Agent 发现一个符合 Intent 但不在清单内的新子 Issue | 通过工具提出新增建议，用户查看变动和理由 | 仅形成待审建议，原正式计划与边界不变；用户确认后才纳入其明确接受的计划和工作范围，退回 / 拒绝不视为接受，也不自动授予额外执行能力 |

### 本轮作者设计走读记录

初轮检查对象为 P1-draft-1 的范围表、低保真交互与 V01–V11；本轮 P1-draft-2 增补 V12–V16，按用户确认将先行看板与后续 Runtime 分层。方法为逐场景核对设计中的入口、可见信息、责任、出口和失败去向；由同一作者进行，不是独立 Reviewer 审查、产品运行或安全实验。

| 走读发现 | 已落实的设计处理 | 仍缺的证据或判断 |
| --- | --- | --- |
| 单独确认 Intent 容易被误作工具授权 | 意图确认与 Grant 批准分开呈现；V02 / V05 检查两个边界 | 真实执行检查、审批保护与越权实验 |
| 一张“完成”卡容易混淆 Run、Git、CI 和验收 | 各项分别展示真实事实及版本；人工验收有独立决定 | 状态观察与远端适配实现 |
| CI 通过仍可能漏掉业务预期 | 标题筛选示例包含“已完成事项也应命中”，交付并列预期 / 实际 | 后续真实项目的测试充分性和人工运行 |
| 停止请求容易被写成已经安全停止 | 执行视图区分请求与实际观察，未知副作用须核查 | X4 及相关组合验证 |
| 授权批准与能力验证的措辞容易混用 | V02 明确为“用户批准有效 Grant 且能力已验证”，不把批准当成能力证明 | 真实能力验证与准入 |
| 保存失败、重复操作或旧页面可能伪造确认 | 增加 V11 与交互失败说明 | 用户评阅建议及真实一致性 / 保护机制 |
| 原稿将完整 Runtime 作为首个交付目标 | 依据 D8.1 改为看板先行，V12 / V13 覆盖外部对话后的记录；具体布局仍为建议 | 看板实现与交互评阅 |
| PR 的文本要求与创建机制不能混为一谈 | 依据 D8.3 加入四段式模板和 V14，保留创建方式未定 | 实际交付时的 PR 责任与能力验证 |

走读结果是上述路径已在设计中明确表达；所有产品运行、安全阻断、CI 集成和用户实际验收仍为未验证。不能据“没有发现其他设计遗漏”推导实现完整或语义正确。

## 对话前置的产品验证要求

对话前置规则以[治理文档](governance.md#对话前置与意图确认)为准。后续实现应通过实际使用观察核查：

- 初始想法存在关键歧义时，Hub 能围绕源头问题澄清，并呈现目标、范围、责任、方案取舍和验证方式。
- 用户能纠正候选 Intent；草案和模型摘要在未经确认时不能被当作正式意图或执行授权。
- 用户确认后，派生交付与后续运行能获得一致的意图及责任上下文；新歧义或意图修改回到适用的商讨授权过程。
- 已确认且仍适用的信息可复用，避免为满足固定轮数而反复提问；用户确认 Intent 与执行 Grant 的效力保持区分。

以上是产品行为要求，不是已实现测试或技术 Pass，也不新增固定对话模板、轮数或技术 Gate。

## 两道交付门禁

两道门禁分别用于发现工程错误与语义漂移，与 G0–G4 研发治理及后文四层技术准入承担不同责任。目标与预期行为以[用户确认的 Intent](governance.md#意图的唯一事实源与变更)为唯一规范事实源。

提交推送前先由 Hub 检查实际改动、影响范围与本地测试。只有适用的本地测试实际通过，且提交推送在当前 Grant 和已验证能力范围内，才进入提交推送；未运行、失败或结果未知不能被记录为通过。该检查由 Hub 承担，不替代最终人工验收，也不预选独立 Reviewer 或检查工具。

| 门禁 | 入口与检查 | 出口及失败行为 |
| --- | --- | --- |
| 第一道：推送后的 CI/CD | Hub 查看与明确交付版本对应的流水线信息，包含静态检查、单元测试等；具体项目检查集合待确定 | 保存版本与真实 CI 结果；出错时在原意图、预算和适用授权内修复，重新执行提交前检查并核查新版本。未运行或结果未知不能视为通过 |
| 第二道：人工介入的实际运行验收 | 用户检查实际运行结果，对照 Intent 及派生 Issue，并核对 Issue / PR 对“本次修改产生了什么影响、有什么结果”的说明 | 留存场景、环境、版本、实际观察与人工验收决定；偏离 Intent 属于语义偏移，返回修复或先与用户商讨意图修改，不能由 Agent 自行改写目标后宣称通过 |

CI 通过不自动证明语义一致；PR 文本或模型声明不能替代实际运行；Issue 与 PR 文字一致也不能替代它们对 Intent 的一致性。重修产生新版本后，须重新判断旧证据是否适用。Hub 可准备验收材料，最终实际验收必须有人介入；运行启动方式、具体场景和证据呈现仍待细化。

意图修改必须先商讨，并在用户明确授权后执行，保留修改前后内容、理由与适用范围。测试失败、实现困难和模型认为替代方案更好，都不能自动使修改生效。具体变更规则以[治理](governance.md#意图的唯一事实源与变更)为准。

本轮没有确认 PR 的具体创建方式或自动 Merge / Release，亦没有授权配置流水线、部署环境或执行远程操作。

## 产品有效性与待确定的验收方法

产品应通过实际使用证明：使用者能够从源头问题解释做了什么、为什么值得做、核心业务与技术逻辑如何产生预期行为，并用对应版本的实际证据核对影响与结果。理解与推进冲突时先理解再推进；目标是减少后期补理解、语义偏移和返工带来的成本，而非只追求执行速度。

现阶段确认的是验收方向。任务样本、比较基线、观察方式和量化阈值尚未确定，不能虚构改善比例，也不能只凭字段齐全、规范文本或 CI 绿灯宣称产品有效。本轮未要求用户参加知识测验或逐项确认所有实施步骤。

## 实验启动前 R1–R7

为避免由被测组件承担其自身失效时的全部保护责任，首次高风险实验优先采用可丢弃 macOS VM 或经审查的等效独立外层保护。使用模拟仓库、模拟秘密与受控网络；候选 Sandbox 失效也不应直接威胁真实宿主机。

| 条件 | Preflight 必须提供的内容 |
| --- | --- |
| R1：独立外层隔离 | 外层保护的实际形态、边界及独立性事实 |
| R2：模拟资源与身份隔离 | 模拟仓库、秘密、身份及受控网络，不暴露真实凭据 |
| R3：被测对象和运行条件明确 | 可识别的组件版本、环境和策略；不以产品名称代替对象身份 |
| R4：正反向用例和标准预先固定 | 可证伪假设、正反向用例、必要组合路径与判定标准 |
| R5：独立观察可用 | 不依赖模型自述或被测组件自我证明的可信观察与证据 |
| R6：预算、异常停止与清理明确 | 资源预算、停止条件、异常处置和清理边界 |
| R7：具体人工授权 | 人工对本次具体对象、范围和条件作出的实验许可 |

X1、X2 必须分别完成 Preflight 与人工 Go/No-Go。X1 的 R1–R6 尚待真实环境采集；目前没有实际执行授权。缺失事实不得以规划、候选名称或本文件存在来替代。

Go 仅允许在批准范围内开始实验，不等于技术 Pass；No-Go 不允许启动该次实验。环境、对象或范围重要变化时，不能沿用不适用的旧许可。Guest 中 Pass 不自动取得宿主机正式执行资格。

## 实验四态退出

预先规定退出与停止行为，是为了避免在证据不足或危险条件下继续试探。具体阈值、预算与清理由各实验的 R4 / R6 固定，不能事后改写标准。

| 状态 | 含义与后续边界 |
| --- | --- |
| Pass | 在所验证对象、版本、环境与策略范围内满足预定标准；不自动授权实现、晋升或其他环境 |
| Fail | 证据表明至少一项预定必要标准未满足；记录失败和影响，不升级能力 |
| Inconclusive | 观察不足、环境不符或结果不明，不能支持通过或明确失败；保留 Unknown，不按 Pass 使用 |
| Unsafe to Continue | 继续实验无法维持批准的安全条件，必须停止并按预定异常处置和清理要求处理；不得以继续取证为由扩权 |

退出时应保留真实观察、适用范围、未验证事项和已知或未知副作用。Evidence 的 Integrity / Applicability / Sufficiency 以[治理规范](governance.md#evidence-与-review)为准。

## 四层准入与可信晋升

技术开发、正式承担可信职责和最终产品验收需要不同依据，不能用同一个 Go 或 Pass 覆盖。

| 层次 | 决定什么 | 不能替代什么 |
| --- | --- | --- |
| 1. Experiment Authorization | 是否许可在具体范围和保护条件下开展某次实验 | 不等于技术 Pass 或 MVP 实现许可 |
| 2. Implementation Go / Scoped Go / No-Go | 是否允许实现、限定范围安全开发或不允许推进 | Scoped Go 不能开放尚未验证的高权限执行能力 |
| 3. Trusted Component Promotion | 候选组件能否依据真实版本、环境和策略的验证证据，经人工晋升承担正式可信职责 | 实现完成或单项实验 Pass 不自动成为可信组件 |
| 4. MVP Acceptance | E1–E4、确定后的产品有效性要求与交付边界是否成立，交付版本、Review 和 Evidence 是否支持人工最终验收 | 组件晋升和 Run 完成都不等于最终验收 |

G0–G4 是[研发治理检查点](governance.md#g0g4-与人工责任)，与上述四层不是编号对应关系。初始文档固化没有作出实验 Go 或实现许可；本次仅有明确的 TypeScript 骨架初始化授权，不能推导完整 MVP Implementation Go、可信晋升或 MVP 验收。
