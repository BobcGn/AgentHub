# MVP 验收与技术验证契约

本文件规定验证对象、准入与证据要求，不是实验执行许可或测试结果报告。**X1–X5 尚未开展正式实验；X1/X2 未获得实际执行授权；不存在已确认的技术 Pass；正式 MVP Implementation Go 尚未作出。** 当前事实以[工程状态](project-status.md)为准。

## 当前 MVP 目标与 E1–E4

本轮产品意图回顾明确：先通过对话澄清意图、责任、边界和验证方式，由用户确认 Intent；人理解方案理由、收益和风险后，再按交付单元推进；Issue 和 PR / Review 应展示 What、Why 与可验证的 Result。较大的 Intent 可以用父 Issue 表达，子单元对应子 Issue，拆分依据源头问题和交付边界。

第一版优先云端模型与 Hub 自有 Harness，保留单主要写入 Run。既有 DeepSeek Loop 是技术起点，本轮未重新指定具体模型或服务商。本地小模型后续可用于辅助 Review 或文档总结；已有 Agent 的适配后置，须另行验证运行时约束。

初始化时的技术验证切片仍可用于一个真实、可复现的小型本地代码缺陷修复：

Issue → 人工批准 Grant → 单主要写入 Run → Hub 自有 DeepSeek Loop → 受控调查、修改和真实测试 → Trusted Git Broker 本地 Commit → Evidence → 绑定 Commit 的 Review。

该切片不再被视为单独足以证明完整产品目标。Hub 负责提交前检查和本地测试，通过后在获准范围内提交、推送并查看 CI 信息；用户介入最终实际运行验收。PR 创建方式、验收场景和最小看板交互仍待细化，完整产品 MVP 边界尚未重新冻结。产品责任明确不构成实际远程操作授权或能力验证。

| 验收项 | 必须证明的结果 |
| --- | --- |
| E1：真实研发交付 | 问题可复现或有明确验收场景；已确认 Intent、派生 Issue、确定版本、提交前检查、本地测试、CI / 运行结果及 PR / Review 影响说明相互对应，并经用户介入实际运行验收。技术切片只能证明其覆盖部分 |
| E2：越权操作阻断 | 超出 Grant 或已验证能力的操作被实际阻断，不能仅以模型承诺为证 |
| E3：权威事实与审批保护 | 不可信指令不能篡改 Intent、其修改授权、正式领域事实、人工审批与可信验收；不能通过擅改目标或验收条件消除实现偏差 |
| E4：中断与安全恢复 | 能识别中断、未知副作用并依据实际状态受限恢复，不能用请求记录代替执行事实 |

Codex 正式适配、完整 MCP、多 Agent、多项目调度、Electron 打包、通用 VM 管理平台、完整 Dashboard、通用 Skill / Workflow 市场仍延期。本地辅助模型不是第一版必要条件。Issue 看板与执行看板结合是产品目标，首版最小呈现和交互范围待确认。

## 阶段一设计检查与后续真实项目验证

2026-10-23 用户明确阶段一可基于既有 Intent 开始，真实项目后续导入验证。本阶段的产品交付是[首版闭环与最小交互草案](architecture.md#阶段一首版交互草案2026-10-23)、候选能力范围、待决定事项及验收方向；不以用户先提供真实项目或任务为开工条件。

阶段一通过文档评阅和场景走读检查以下设计要求。表中列出预期行为，没有执行结果，也不构成产品测试或技术 Pass：

| 走读情况 | 设计应如何处理 |
| --- | --- |
| 意图尚有关键歧义或未经用户确认 | 继续澄清并明确展示草案及未决事项，不把候选内容当作正式意图进入执行 |
| 拟拆分的子 Issue 与源头问题没有独立交付理由 | 说明或调整边界，不为填满流程而继续拆分 |
| 执行中需要改变意图或降低验收条件 | 展示原因、影响和变更提案，先商讨并获得明确授权 |
| 提交前本地测试失败或结果未知 | 留存真实状态并修复或核查，不能视为本地检查通过后提交推送 |
| 推送后 CI 失败 | 关联目标版本，在原意图、预算和授权内返工；新的交付版本重新判断证据适用性 |
| Issue / PR 说明一致，但实际行为偏离 Intent | 人工实际验收应识别偏差并退回，不能仅凭文本一致或 CI 通过判定完成 |
| 中断后文件、进程或提交结果不明 | 核查副作用和当前授权，不假定成功、回滚或可以直接重试 |

阶段一完成需要用户评阅并确认首版范围、必要交互与重要取舍。尚未决定的布局和 PR 创建方式应列为待决定事项，不自动升级为已确认设计；设计确认不替代实现准入。

后续能力就绪并取得相应授权后，再导入真实项目或任务，采集本地测试、CI、运行观察和人工验收依据，检查 E1–E4 及产品有效性。真实项目验证的场景、比较基线和评价方法应在执行前明确，场景走读或模拟结果不能证明实际推进稳定性和可理解性已经改善。工程侧 X1–X5 和技术准入仍按后文处理。

## 对话前置的产品验证要求

对话前置规则以[治理文档](governance.md#对话前置与意图确认)为准。后续实现应通过实际使用观察核查：

- 初始想法存在关键歧义时，Hub 能围绕源头问题澄清，并呈现目标、范围、责任、方案取舍和验证方式。
- 用户能纠正候选 Intent；草案和模型摘要在未经确认时不能被当作正式意图或执行授权。
- 用户确认后，派生交付与后续运行能获得一致的意图及责任上下文；新歧义或意图修改回到适用的商讨授权过程。
- 已确认且仍适用的信息可复用，避免为满足固定轮数而反复提问；用户确认 Intent 与执行 Grant 的效力保持区分。

以上是产品行为要求，不是已实现测试或技术 Pass，也不新增固定对话模板、轮数或技术 Gate。

## 两道交付门禁

两道门禁分别用于发现工程错误与语义漂移，与 G0–G4 研发治理及后文四层技术准入承担不同责任。目标与预期行为以[用户确认的 Intent](governance.md#意图的唯一事实源与变更)为唯一规范事实源。

提交推送前先由 Hub 检查实际改动、影响范围与本地测试。只有适用的本地测试实际通过，且提交推送在当前 Grant 和已验证能力范围内，才进入提交推送；未运行、失败或结果未知不能被记录为通过。该检查由 Hub 承担，不替代最终人工验收，也不预选独立 Reviewer 或检查工具。

| 门禁 | 入口与检查 | 出口及失败行为 |
| --- | --- | --- |
| 第一道：推送后的 CI/CD | Hub 查看与明确交付版本对应的流水线信息，包含静态检查、单元测试等；具体项目检查集合待确定 | 保存版本与真实 CI 结果；出错时在原意图、预算和适用授权内修复，重新执行提交前检查并核查新版本。未运行或结果未知不能视为通过 |
| 第二道：人工介入的实际运行验收 | 用户检查实际运行结果，对照 Intent 及派生 Issue，并核对 Issue / PR 对“本次修改产生了什么影响、有什么结果”的说明 | 留存场景、环境、版本、实际观察与人工验收决定；偏离 Intent 属于语义偏移，返回修复或先与用户商讨意图修改，不能由 Agent 自行改写目标后宣称通过 |

CI 通过不自动证明语义一致；PR 文本或模型声明不能替代实际运行；Issue 与 PR 文字一致也不能替代它们对 Intent 的一致性。重修产生新版本后，须重新判断旧证据是否适用。Hub 可准备验收材料，最终实际验收必须有人介入；运行启动方式、具体场景和证据呈现仍待细化。

意图修改必须先商讨，并在用户明确授权后执行，保留修改前后内容、理由与适用范围。测试失败、实现困难和模型认为替代方案更好，都不能自动使修改生效。具体变更规则以[治理](governance.md#意图的唯一事实源与变更)为准。

本轮没有确认 PR 的具体创建方式或自动 Merge / Release，亦没有授权配置流水线、部署环境或执行远程操作。

## 产品有效性与待确定的验收方法

产品应通过实际使用证明：项目推进更稳定，使用者能够依据 Issue 与交付说明理解要做什么 / 做了什么、为什么这样做，以及结果与证据；理解速度与推进速度能够取得平衡。

现阶段确认的是验收方向。任务样本、比较基线、观察方式和量化阈值尚未确定，不能虚构改善比例，也不能只凭字段齐全、规范文本或 CI 绿灯宣称产品有效。本轮未要求用户参加知识测验或逐项确认所有实施步骤。

## TypeScript 工程初始化检查

本次检查用于判断工程是否可安装、静态检查、编译和启动，范围依据 [D7.2](decisions.md#typescript-工程初始化范围2026-10-23)。它不执行模型调用、Agent 工具、Git 操作或安全实验，也不要求先执行高风险 X1–X5 才能验证无业务能力的工程骨架。

| 命令或检查 | 能支持的判断 | 失败行为与证据边界 |
| --- | --- | --- |
| npm ci | 锁文件与当前环境可恢复开发依赖 | 安装失败如实记录；依赖可安装不等于安全审计或产品可用 |
| npm run check | 当前 src 的 TypeScript 静态检查通过 | 目前只含类型检查；没有单元测试、格式检查或运行验证 |
| npm run build | 当前 src 可编译到 dist | 编译失败停止，不能继续用旧产物宣称新代码可运行 |
| npm start | 编译入口可启动并输出骨架说明 | 只验证入口进程，不证明 Loop、工具控制或交付闭环存在 |
| 本地文档链接与锚点检查 | 已检查文档的本地引用可解析 | 不证明规范已实现、产品有效或安全边界成立 |

检查的实际运行环境与结果记录在[工程状态](project-status.md)。当前无自动化行为测试，tests 仅占位；后续业务行为应增加与 Intent、失败边界对应的有效测试，并把命令接入开发检查。不得通过伪造测试、模型自述或入口成功输出来宣称 E1–E4、X1–X5、可信组件晋升或人工验收通过。

## X1–X5 技术实验

| 实验 | 主要验证问题 |
| --- | --- |
| X1：macOS Sandbox | 受限进程机制能否在指定环境允许合法工作并阻断越权 |
| X2：Trusted Git Broker | 能否完成获准本地 Commit，同时保护 Git 管理状态并限制间接权限 |

每项实验均需独立人工授权、可证伪假设、正反向测试、必要的组合越权检查、独立观察和可信证据，并预先固定预算、停止与清理要求。X3–X5 的逐项用例尚未在本次输入中确认，不在此虚构完整契约。

## 实验启动前 R1–R7

为避免由被测组件承担其自身失效时的全部保护责任，首次高风险实验优先采用可丢弃 macOS VM 或经审查的等效独立外层保护。使用模拟仓库、模拟秘密与受控网络；候选 Sandbox 失效也不应直接威胁真实宿主机。

| 条件 | Preflight 必须提供的内容 |
| --- | --- |
| R1：独立外层隔离 | 外层保护的实际形态、边界及独立性事实 |
| R2：模拟资源与身份隔离 | 模拟仓库、秘密、身份及受控网络，不暴露真实凭据 |
| R3：被测对象和运行条件明确 | 可识别的组件版本、环境和策略；不以产品名称代替对象身份 |
| R4：正反向用例和标准预先固定 | 可证伪假设、正反向用例、必要组合路径与判定标准 |
| R5：独立观察可用 | 不依赖模型自述或被测组件自我证明的可信观察与证据 |
| R6：预算、异常停止与清理明确 | 资源预算、停止条件、异常处置和清理边界 |
| R7：具体人工授权 | 人工对本次具体对象、范围和条件作出的实验许可 |

X1、X2 必须分别完成 Preflight 与人工 Go/No-Go。X1 的 R1–R6 尚待真实环境采集；目前没有实际执行授权。缺失事实不得以规划、候选名称或本文件存在来替代。

Go 仅允许在批准范围内开始实验，不等于技术 Pass；No-Go 不允许启动该次实验。环境、对象或范围重要变化时，不能沿用不适用的旧许可。Guest 中 Pass 不自动取得宿主机正式执行资格。

## 实验四态退出

预先规定退出与停止行为，是为了避免在证据不足或危险条件下继续试探。具体阈值、预算与清理由各实验的 R4 / R6 固定，不能事后改写标准。

| 状态 | 含义与后续边界 |
| --- | --- |
| Pass | 在所验证对象、版本、环境与策略范围内满足预定标准；不自动授权实现、晋升或其他环境 |
| Fail | 证据表明至少一项预定必要标准未满足；记录失败和影响，不升级能力 |
| Inconclusive | 观察不足、环境不符或结果不明，不能支持通过或明确失败；保留 Unknown，不按 Pass 使用 |
| Unsafe to Continue | 继续实验无法维持批准的安全条件，必须停止并按预定异常处置和清理要求处理；不得以继续取证为由扩权 |

退出时应保留真实观察、适用范围、未验证事项和已知或未知副作用。Evidence 的 Integrity / Applicability / Sufficiency 以[治理规范](governance.md#evidence-与-review)为准。

## 四层准入与可信晋升

技术开发、正式承担可信职责和最终产品验收需要不同依据，不能用同一个 Go 或 Pass 覆盖。

| 层次 | 决定什么 | 不能替代什么 |
| --- | --- | --- |
| 1. Experiment Authorization | 是否许可在具体范围和保护条件下开展某次实验 | 不等于技术 Pass 或 MVP 实现许可 |
| 2. Implementation Go / Scoped Go / No-Go | 是否允许实现、限定范围安全开发或不允许推进 | Scoped Go 不能开放尚未验证的高权限执行能力 |
| 3. Trusted Component Promotion | 候选组件能否依据真实版本、环境和策略的验证证据，经人工晋升承担正式可信职责 | 实现完成或单项实验 Pass 不自动成为可信组件 |
| 4. MVP Acceptance | E1–E4、确定后的产品有效性要求与交付边界是否成立，交付版本、Review 和 Evidence 是否支持人工最终验收 | 组件晋升和 Run 完成都不等于最终验收 |

G0–G4 是[研发治理检查点](governance.md#g0g4-与人工责任)，与上述四层不是编号对应关系。初始文档固化没有作出实验 Go 或实现许可；本次仅有明确的 TypeScript 骨架初始化授权，不能推导完整 MVP Implementation Go、可信晋升或 MVP 验收。
