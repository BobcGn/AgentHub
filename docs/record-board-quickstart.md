# 正式 Requirement 看板试用

日期：2026-10-26。首页现在使用正式 JSON 项目：卡片是 Requirement，Unit / Story / Bolt Plan 在需求详情中按需出现。当前由本人记录、核对与接受，当前已新增脚本化 Harness 运行区及人端候选应用，见[Harness 指南](harness-quickstart.md)；尚未接入真实 LLM 或代码执行。确定性校验不代替真实证据与人工验收。

## 更新与启动

已有账户和旧库可以继续使用，无需重新 setup 或删除数据。在项目根目录：

```sh
npm run check
npm run build
npm start
```

如果原服务还在运行，先在它所在终端按 Ctrl-C 停止，再执行 npm start。打开 http://127.0.0.1:4317 并刷新浏览器；重新登录使用原人端密码。新装项目的环境与 setup 操作见[安装说明](board-quickstart.md#安装与首次启动)。

默认账户与旧业务仍在 .agenthub/board.sqlite；正式 JSON 项目保存在该数据库同级的 record-projects 目录，每个项目一个文件。设置 AGENTHUB_DB 时，新记录默认随它放在同级目录；可通过 AGENTHUB_RECORDS_DIR 明确更改位置，重启时保持配置一致。它只是应用内部保存位置，没有目录管理、Git 回滚或团队协作功能。

## 新建与编辑

1. 点击“新建/导入项目”，记录通过对话明确的初始 Intent：问题、预期结果、包含 / 排除范围与约束；本人确认后创建。界面不会自动载入样例或改写旧项目。
2. 点击“新增 Requirement”，填写问题、预期结果、理由、影响、边界与验收条件。draft 可尚无验收条件，planned 及以后必须明确至少一项；review 要有已经发生的实际结果。先检查并预览差异，再勾选确认保存。
3. 看板只显示 Requirement，列为待规划、待开始、进行中、待核对、已记录完成。拖动先进入预览；拖入完成列会进入独立整体接受，不直接保存完成。
4. 打开卡片，按需要添加 Unit、Story、Bolt Plan。Story 可直接归属 Requirement 或选择本需求的 Unit；Bolt Plan 必须选择本需求至少一个 Story。每项有自己的理由、影响与验收条件，不要求机械填满各层。
5. 在详情中追加长期关键信息、最小出处、验收证据及逐条件核查；编辑器支持分块表单和高级记录。高级编辑同样经过完整结构、归属、引用和权限检查，不能修改 ID、静默转移归属或伪造整体接受。来源和观察证据保留原文，纠正时追加新记录。
6. 实际产出记录 what、why、actualImpact 与适用证据；最终 PR 仅挂在 Requirement，记录地址与“做了什么、为什么、如何验证、影响 / 结果”。这里只登记已有 PR，不创建或推送 PR。

每次编辑都必须说明为什么变化，保存前可查看修改前后及关联变化；历史保留理由、差异和旧核查 / 接受被撤销的影响。人工写入出处由服务产生，不能因一条引用存在就宣称内容真实或已获执行授权。

## 完成与重新核对

子产物标记完成前，必须有实际结果和对应每条验收条件的适用证据及通过核查，模型审查不能作为唯一依据。Requirement 完成还需要现有子产物全部完成、整体条件通过、唯一 PR 及独立人端整体接受。补充接受说明选填；未达到条件会展示合同错误，正式记录保持原状。

修改已有工作内容后，原对应核查回到 unknown；修改已接受需求或其子产物会让当前整体接受失效。旧事实保留在变更历史，不能继续拿旧通过为新内容背书。状态是手动记录，程序不声称已执行测试、检查过链接或验证过证据真实性。

界面当前展示已确认 Intent 正文，通用记录编辑器不允许修改；迁移后的 proposed 意图表示可通过单独入口登记已完成的商讨和明确确认，但不能用该入口改写正文。需要修改意图正文时，仍须先商讨并明确授权；当前新 JSON 界面尚无完整 Intent 修订流程。

## 旧项目迁移

1. 首页“旧项目待核对迁移”中点击对应预览。此时只读原库，不写新项目；一个旧正式 Issue 映射成一个 Requirement 草案，Unit / Story / Bolt Plan 留空。
2. 核对转换 JSON。旧父子关系保留映射及来源；原方案、收益、风险、讨论和批准文字按来源保留，不自动成为新验收、passed 或已完成产物。缺少的目标 / 边界明确显示待核对，不自行推断。
3. 本人勾选“已核对迁移预览，同意导入项目并保留旧记录”并确认，才另存正式项目。预览后旧内容变化会拒绝旧预览，须重新打开核对。
4. 迁移后需求为草案，意图的新表示仍为 proposed；迁移确认不等于确认新拆解或完成。原始批准历史、父子与旧记录可从详情只读查看；意图表示另行核对并明确确认后，才可进入正式计划。
5. 已迁移旧项目的业务写入被应用层拒绝，避免两份正式内容各自变化。旧库不删除，旧令牌不扩权到新 JSON；可在“查看旧项目来源（只读）”弹窗中撤销原工具令牌。未迁移项目可继续从“旧版工作区”使用原流程。

B1–B3 CLI 仍服务于未迁移的旧模型；当前新 JSON 项目接口只允许人端会话，不接受工具令牌。新结构的外部工具提议 / 审批与 Harness 适配后续再设计，不能用旧 CLI 直接写新 Requirement。

## 自动同步与失败行为

通过当前 Hub HTTP 服务写入成功后，页面接收无业务内容的 SSE 通知，再读取经过鉴权的最新快照。编辑草稿保留；修订号变化时先阻止旧提交，再由本人核对新差异。网络或保存失败显示错误，不以界面乐观更新宣称成功；结果不明时先刷新核对，避免盲目重复。直接编辑磁盘文件或另一进程写入不在当前通知覆盖范围。

项目文件采用临时写入、fsync 和原子替换；修订检查适用于当前单服务进程，不是多进程分布式锁。损坏 / 非法项目文件会报错而不自动覆盖；暂存失败保留旧正式文件。默认新目录权限 0700、文件 0600，不证明同一 OS 用户下的防篡改或可信审批隔离，详见[安全边界](security.md#正式-json-项目的接口与宿主边界)。

测试与截图使用隔离演示数据。实际用户数据是否迁移、内容是否符合 Intent、证据是否可信及最终是否接受，仍由本人判断。
