## 当前范围：JSON 合同与正式看板

用户先明确只建设 JSON Schema，之后明确要求直接替换正式看板并确定保存与旧数据适配，选择人端核对迁移预览后另存 JSON。该正式看板轮次实现了 Requirement 状态列、分块详情、手动分层编辑、JSON 持久化及迁移预览；当时不含 Harness。用户后续已授权并实现首节的最小 Harness，目录 / Git 管理及团队协作仍未建设。当时曾采用“一个 Requirement 对应一个最终 PR”的历史规则（该规则已于 2026-10-30 由 SC-005 废除并升级为可选 0..N 个 PR，见[路线图](json-schema-roadmap.md)），内部可选 Unit / Story / Bolt Plan 分层、分别验收；长期 JSON 提炼关键内容并保留最小出处。现行合同见[说明](json-schema-contract.md)，使用见[指南](record-board-quickstart.md)。下文总体候选以当前范围与实际状态为准。

## 两项建设目标

1. 统一人能读、程序能校验、Harness 能消费的记录合同，避免看板、Markdown 和模型上下文各自维护不同的正式内容。
2. 建立自有模型执行循环与外部适配边界，使 LLM 的候选输出经过结构、版本、权限和人工检查点处理后才能产生适用副作用，并保存可观察的运行过程。

图示中可借鉴的是 Backlog / Todo / In Progress 等状态列和 Issue 卡片交互；图中具体项目、数量和任务内容不是 AgentHub 需求。用户接受类似 Multica 的状态看板方向，具体枚举、拖拽行为、配色和布局仍待设计。卡片作为概览，详情按记录合同分块，而不是把全部 JSON 原样铺在界面。

## Markdown、实例、Schema 与存储

| 组成 | 责任 | 边界 |
| --- | --- | --- |
| Markdown | 可选的自然语言说明、备选方案论证、设计和实验材料；对话为短期上下文，长期 JSON 提炼关键内容 | 自然语言不能自行生成正式授权、执行成功或验收结论 |
| JSON 实例 | 保存具体对象、适用版本、状态、引用与证据索引，供服务 / Harness 使用 | 候选与正式内容区分；模型不得自填可信人端字段使其生效 |
| JSON Schema | 定义实例的类型、字段、枚举、条件必填与合同版本 | 它是合同，不是数据；跨对象引用、状态迁移和权限仍须用例检查 |
| 正式 JSON 与现有 SQLite | 新项目正式内容写 JSON；SQLite 维护账户与旧来源，复用会话、Origin、通知、版本与幂等原则 | 旧项目确认迁移后业务只读，避免同一项目两套正式内容同时写入；不是团队 / 目录管理功能 |
| 看板 / 导出 / 模型上下文 | 从适用版本的正式数据和获准材料生成不同表达 | 看板列、渲染结果或模型摘要不取代正式事实 |

Schema 版本、对象内容版本、Intent 版本及实际 Run / 交付版本含义不同，设计时须明确对应与失效行为。Markdown 与结构化实例通过稳定引用关联，明确哪部分内容由谁维护，避免双向自由覆盖。Draft 2020-12、Ajv 8.20.0 已用于当前合同；整体导入导出、团队与 Git 管理仍未实现。

## 结构化内容与看板分块候选

以下是需要收敛的内容分块，不是已经冻结的字段名或所有对象都必填的统一大表。Intent、Requirement、Unit、Story、Bolt、Standards 等关系仍以[治理](governance.md#inception-工件与-standards)为准，不能因为 UI 卡片相同就混成一个领域对象。

| 详情分块 | 对应结构化信息 | Harness 与界面的使用 |
| --- | --- | --- |
| 问题与意图 | 源头问题、预期结果、边界、适用 Intent 及版本 | 解释本项为什么存在，确定后续上下文适用性 |
| 交付关系 | 关联需求、Unit / Story、父子 Issue、依赖与适用 Standards 引用 | 组织能力边界与可验证交付，不机械填满所有层级 |
| 方案与解释 | 备选方案收益风险、影响范围、核心业务与技术机制、推荐依据 | 为后续 LLM 解释和人工判断提供合同 |
| 对话与未决问题 | 原文 / 摘要引用、参考资料、问题与回答、适用对象 / 方案版本 | 后续追问和理解记录可回到具体候选，避免批准前对话散落 |
| 计划与运行 | Bolt / Run 引用、输入版本、工作状态、预算、阶段与实际事件 | 明确计划和观察，展示真实进展与停止原因 |
| 验证与证据 | 预期验收场景、实际观察、环境 / 版本、证据来源与局限 | 区分“准备怎样验证”和“实际验证出了什么” |
| 决定与历史 | 候选差异、人工决定、授权引用、变更理由与影响 | 继承现有审批及版本规则，保留历史而非覆盖 |

工作状态、审阅决定、Run 状态和证据结果应分别建模。Backlog / Todo / In Progress / Blocked / Review / Done 可作为看板枚举讨论候选；从某列拖到另一列必须走有效状态迁移，不允许借此跳过权限、人工决定或验收条件。未接 Runtime 时不能把状态更新显示为真实代码执行；Done 的适用完成条件与最终人工验收关系须先定义。

## 最小 Harness 职责候选

| 部分 | 需要解决的问题 | 首个可验证出口 |
| --- | --- | --- |
| 模型端口与适配 | Harness 不绑定某一服务商 SDK，后续替换云端模型仍保留同一合同 | 可使用脚本化模型替身验证接口；不冒充真实模型表现 |
| 上下文组装 | 读取适用 Intent、工作项、Standards、决定、有效范围和必要原文 | 输出有来源 / 版本且受范围约束的输入快照 |
| 执行循环与 Run | 组织模型提议、工具结果反馈、预算、错误、取消及停止原因 | 循环能确定性结束，失败和未知不写成成功 |
| 候选与工具分发 | 对模型输出先做结构、关系、版本与能力检查，再分发到获准用例 | 非法、越界、过期提议无正式副作用；必要时等待人工 |
| 人工检查点 | 在缺少关键判断、授权或遇到意图变更时等待并保留上下文 | 模型不能自行生成“用户已理解 / 批准”；恢复时重查版本与授权 |
| 事件、记录与恢复 | 保存请求、实际观察、决定引用与中断状态，避免黑盒推进 | 可以重建发生了什么；未知副作用不盲目重复执行 |

保持现有 TypeScript 层次：domain 定义语义，application 协调用例，harness 组织模型循环，infrastructure 提供模型 / 存储 / 工具适配，presentation 呈现和交互。接口或提示词不等于安全隔离；执行器、Shell、Git、网络和凭据能力仍按对应验证与授权逐项开放。

## 建议交付次序与完成条件

1. **记录合同与样例。** 明确最小对象、字段、版本、引用、状态迁移及可信字段职责，准备 Markdown + JSON 合法 / 非法样例和对应 Schema。用 AgentHub 自身的已确认 Intent 展示含义与分块映射，说明关键取舍；不要求先做完整 LLM 审查或成熟决策 UI。完成条件是人能理解合同，程序能识别结构错误。
2. **合同校验与现有数据衔接。** 当前已实现 Schema / 关系校验与正式 JSON 保存；复用现有会话和服务基础，按已确认迁移预览规则处理旧数据、权限、版本冲突和幂等。完成条件是非法结构、未知引用、越界、失效版本及不允许的迁移不会改变正式事实；看板可从样例或适配数据投影。
3. **最小 Harness。** 建立模型端口、上下文快照、Run 循环、受控用例调用、人工等待、停止 / 恢复和事件记录，用脚本化模型替身验证。首个切片优先消费记录、形成候选、等待人端，具体可执行能力按授权和验证逐步加入。完成条件是循环、边界与记录机制可重复验证；不据此宣称真实 LLM 遵循 Intent。
4. **接入一个云端 LLM 验证纵向链路。** 明确服务商与调用范围后，验证读取 Intent / 记录、生成结构化候选、必要追问、等待人工决定、获准推进和记录结果；观察真实错误和语义偏移。模型参与的解释 / 审查效用在此阶段验证，最终人工验收保留。
5. **完善分状态、分块看板。** 用户已将正式看板前移到当前 JSON Requirement，现可手动记录；后续与 Harness 适配，以真实事件逐步展示进度、候选和证据。完成条件是列状态和详情分块对应同一正式数据，拖动不绕过用例，来源 / 版本清楚，自动同步和草稿保护保留。它不成为接通最小 Harness 的前置阻塞。
6. **真实任务与后续交付。** 扩充相应 B4 端到端 / 故障验证，并在能力就绪和授权明确后接通本地测试、Git / CI 与实际运行验收。依据原 Intent 判断理解、可控推进和证据是否改善，再扩展本地辅助模型或已有 Agent 适配。

以上为建议切片，用户已确定的是记录体系、结构化看板方向与 Harness 建设优先级；具体 Schema、状态枚举、模型服务商、工具能力和界面布局仍待相应设计和验证。B1–B3 的源码与历史证据保留；独立 Schema 和正式 JSON 看板已有实现，当前证据见[状态](project-status.md#正式-json-项目看板与迁移2026-10-25)。最小脚本化 Harness 现已实现；真实模型调用及代码执行仍未实现。
