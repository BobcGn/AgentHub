## 三个交付单元与执行顺序

以下是供阶段执行使用的交付单元候选，顺序为 **P1-1 → P1-2 → P1-3**。编号只用于本地计划定位，不代表已创建 GitHub Issue、已批准产品 Grant 或已完成工作。三个单元分别解决范围、交互和验证问题，不再按文档章节或操作拆成更多子 Issue。

1. **P1-1：收敛首版范围与责任。**

   要解决的问题：已有产品目标较完整，但首版必须做到什么、允许延后什么，尚未冻结。

   入口：既有 Intent、阶段一交互草案、当前 MVP 与延期范围。先做差异整理，不重复发明产品目标。

   执行：

   - 用一个设计示例串起“对话 → 确认 Intent → 按问题边界组织 Issue → 理解方案 → 授权执行 → 本地检查 → 提交推送与 CI → 人工验收”；示例不是新增需求或真实项目证据。
   - 列出首版必要行为、可延期能力和仍需判断的事项，并说明每一项与源头问题的关系。区分“首版需要设计覆盖”与“阶段一要实现”。
   - 明确用户、Hub 和 Agent 的责任；对 PR 创建方式等未决项提出可比较的建议，说明收益、风险、依赖和失败后的责任归属。
   - 保留已有云端优先、单主要写入 Run 和双门禁要求；不为简化实现而自行删减意图。

   产出：更新[架构草案](architecture.md#阶段一首版交互草案2026-10-23)与[当前 MVP 边界](validation.md#当前-mvp-目标与-e1e4)，形成首版范围候选及重要未决事项。

   完成标准：每项首版行为有明确的问题依据、责任方和可观察结果；新增建议与已有确认可区分，重要取舍有方案和影响说明。需要用户决定的项明确保留，不由 Agent 代为确认。

2. **P1-2：定义最小交互与流程衔接。**

   要解决的问题：用户如何在推进中持续找到原始意图、理解选择、看清实际动作并判断交付。

   入口：P1-1 的范围候选。未决项不妨碍的部分可继续设计，依赖未决取舍的部分标为候选分支。

   执行：

   - 基于现有六类信息区域，形成最小信息组织建议和文字线框；不把六类区域直接等同于六个页面，也不预先选择前端框架。
   - 为关键操作说明用户看到的信息、可做的决定、进入条件、结果和失败后的去向；分别展示意图确认、执行授权、意图修改与最终验收。
   - 说明 Issue 中预期的 What / Why / Result 如何与执行观察、版本明确的交付说明对应；模型分析、真实动作和人工判断采用可区分的表达。
   - 覆盖纠正草案、暂不确认、等待判断、失败返工、中断和结果未知；不以额外的逐步审批拖慢正常授权内推进。

   产出：在[架构文档](architecture.md)细化交互草案与文字线框；领域语义继续引用[治理文档](governance.md)，避免在页面描述中产生第二套规则。

   完成标准：从一个初始想法可走读到人工最终判断，且每个关键衔接都能说明“为什么可以继续、依据是什么、谁决定、不能继续时怎么办”。未确认布局和交互仍标为建议。

3. **P1-3：建立验收对应关系并准备阶段评阅。**

   要解决的问题：防止方案文字看似一致，实际却缺少能发现语义偏移的验证要求。

   入口：P1-1 的范围候选与 P1-2 的交互方案。

   执行：

   - 为首版关键行为建立“适用 Intent / Issue 预期 → 用户可见结果 → 所需证据 → 人工判断”的对应关系，标明适用版本和证据缺口。
   - 按[已有设计检查场景](validation.md#阶段一设计检查与后续真实项目验证)逐项走读，补足交互与责任说明，不把走读写成运行测试通过。
   - 汇总已确认内容、可选方案、剩余未知项和重要取舍，提供适合用户评阅的阶段材料。
   - 列出下一阶段需要取得的技术事实、需要验证的假设和相应准入；不在本阶段执行 X1–X5，也不预先指定数据库、Sandbox 或模型供应商。
   - 为后续真实项目验证保留实际场景、比较基线和评价方法的待办；无需现在提供真实项目或虚构改善阈值。

   产出：更新[验证契约](validation.md)、[工程状态](project-status.md)，并仅在用户明确决定后更新[决策索引](decisions.md)。

   完成标准：范围、交互、责任和验证要求可相互追溯，关键未知项没有被假定为已解决，用户有足够材料评阅首版方案；用户确认后，才记录阶段一完成及获确认的具体范围。

## 设计走读与证据边界

以下为预定检查，没有实际执行结果；不新增测试框架、固定问卷或人工 Gate。

| 场景 | 阶段一方案应说明的处理 |
| --- | --- |
| 关键意图尚未明确，模型已提出拆分 | 继续澄清，展示草案及未决项，不把模型建议当正式意图 |
| 一个 Intent 被拆成大量操作型子 Issue | 回到源头问题说明边界，合并缺少独立交付理由的单元 |
| 用户已确认 Intent，但尚未授权执行 | 保持意图确认与 Grant 的区别，不自动推进真实动作 |
| 实现遇到困难，模型建议降低预期 | 展示证据、影响与变更提案；未经商讨授权，继续以原 Intent 判断 |
| 提交前本地检查失败或结果未知 | 修复或核查，不能进入“本地检查已通过”的交付分支 |
| 远端 CI 失败并返工产生新版本 | 在原目标与授权内修复，重新检查并核对证据适用版本 |
| Issue / PR 文字一致、CI 通过，但运行行为偏离意图 | 用户实际验收识别偏差并退回；不能通过改写记录让偏差消失 |
| 执行中断或工具结果不明 | 展示已知、未知及所需核查，不能假定成功、回滚或可重试 |

具体规范仍由[治理](governance.md)、[安全](security.md)和[验证](validation.md)维护。示例、文字线框与设计走读仅支持方案评阅，不证明 E1–E4、X1–X5 或推进稳定性改善。

- 文档链接和规范一致性检查通过，交付说明保留实际改动、未验证事项与版本边界。
- 已整理下一阶段的技术事实缺口和准入事项；阶段一确认不替代实验许可、正式实现准入或 MVP 验收。
