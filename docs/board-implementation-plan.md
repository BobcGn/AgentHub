## 第一轮遗漏检查与交付目标

已确认的 D8.1–D8.7 足以支持编码规划：先做项目 Intent / Issue 看板；外部 Agent 通过 CLI 或等效工具写入；用户理解方案、收益风险和验证依据后决定；普通记录只可在划定边界内直接保存；清单外新增工作先待审；PR 保留四段式规范与用户补充证据。没有需要重新讨论总体意图才能开始规划的业务缺口。

仍需处理的是工程决策：人端与工具端如何区分身份、如何表示和检查写入边界、如何保证审批针对同一版本并完整落库、如何呈现计划与待审差异。以下为具体候选方案，不能把本计划当作这些机制已得到用户接受、实现或安全证明。

看板可用的最小证明：用户建立项目及初始 Intent → 授予明确工具写入范围 → 外部 CLI 提交新增 Issue 建议 → 看板显示变动、理由和验证方式 → 用户作出决定 → 只有确认后才出现正式 Issue；在已允许范围追加记录，重启后仍能读到真实保存的内容。

## 推荐工程基线与取舍

沿用单包 TypeScript / Node.js / npm，复用现有目录。下表保留规划时的候选与取舍；B1 现已采用 React / Vite、本地 Node HTTP、better-sqlite3 和原生参数解析，精确依赖已安装并写入锁文件；替代方案仍为未采用候选。

| 位置 | 建议 | 理由与主要代价 |
| --- | --- | --- |
| 看板界面 | React + TypeScript，Vite 构建，本地浏览器使用 | 对概览、Issue 详情、差异和待审列表组织组件；增加浏览器构建配置。替代为原生 TS 界面，依赖更少但需手工维护复杂交互 |
| 本地 Hub 服务 | Node.js / TypeScript，提供统一查询、提交和人端决定入口 | CLI 和界面共享同一业务规则；不能将 localhost 当作已认证身份。具体路由框架按实现规模选最小必要能力 |
| 持久化 | SQLite，由服务统一写入；驱动优先评估 better-sqlite3 | 正式记录与决定可在事务中一起更新；需验证当前 macOS / Node 24 环境的原生依赖安装与打包。替代为 node:sqlite，但须核对当前 Node 24 对应 API 与稳定性，不以较新 Node 文档代替本环境验证 |
| CLI | 独立命令入口，调用 Hub 服务；优先使用 Node 原生参数解析 | Agent 可获得稳定的结构化返回，避免 CLI 另写一套存储和规则；命令名及协议仍是候选 |
| 测试 | 领域与应用测试、真实存储集成测试、浏览器端到端测试 | 覆盖实际边界、审批和持久化故障；不为占位入口编写形式测试，也不以覆盖率代替业务结果 |

选择依据：React 官方提供[组件及状态组织方法](https://react.dev/learn/thinking-in-react)，Vite 官方提供[TypeScript / React 模板与构建说明](https://vite.dev/guide/)。SQLite 的[事务保证](https://www.sqlite.org/transactional.html)适合避免正式记录与决定只保存一半，但不提供用户身份或 Agent 隔离。[better-sqlite3](https://github.com/WiseLibs/better-sqlite3)作为驱动候选；Node 提供[parseArgs](https://nodejs.org/api/util.html#utilparseargsconfig)。这些资料支持候选方案，不构成本机兼容或安装通过的证据。

## 最先解决的权限与一致性问题

- 工具端只取得明确范围的查询、普通记录追加和提案提交能力；人工确认入口需要独立、可验证的人端身份。不能用可随意传入的 actor 字段或 --role human 证明人工操作，也不能只在 CLI 隐藏批准命令而让直接接口调用绕过。
- 在 B1 内确定人端会话和工具凭据的发放、使用及撤销方式，检查后端鉴权、请求来源与重复请求。未建立明确身份边界时，仅用演示数据开发交互，不赋予其可信审批或生产记录资格。
- 写入范围建议显式关联项目、Intent、允许的 Issue 集合及操作；工具调用上下文决定权限，业务输入不能自行携带“已批准”或更大的范围。新 Issue 建议可按允许的提案入口保存，但其正式纳入仍需用户决定。
- 提案包含被修改对象、基于的版本、前后差异、理由和预期验证。用户决定绑定所展示的提案版本；内容或基准已变化时拒绝沿用旧决定，要求重新核对。
- 正式记录、提案处理结果和决定在同一事务内更新；重复提交使用幂等处理，版本冲突和保存失败如实返回，不产生部分生效或虚假成功。
- 数据目录不作为 Agent 的直接写入接口，工具只通过 Hub 提交。仅把文件移出仓库或分开 Token 不能证明同一操作系统用户下的隔离。B1 已实现应用入口内的权限检查；完整保护主张仍受[安全边界](security.md#看板开发中的审批与宿主边界)和对应验证约束。

## 四个编码交付单元

编号 B1–B4 用于代码计划定位，尚未创建远程 Issue。顺序为 B1 → B2 → B3 → B4，每项都以可运行的结果结束，不按技术层拆成只能等待后续才能使用的孤立交付。

1. **B1：最小提案审批闭环。**

   先核对依赖兼容和身份区分方案，再做一个最小贯穿切片：用户在界面建立项目 / 初始 Intent 与明确工具范围；CLI 提交新增 Issue 建议；界面显示变动内容、理由和预期验证；用户确认后创建正式 Issue。拒绝或退回保持原计划。

   同时实现实际存储、被审版本检查和事务保存。界面、服务和 CLI 均需真实连通，不以静态页面或内存假数据代替该项完成。

   完成标准：演示数据可贯穿全流程并在重启后保留；工具端直接调用人端确认入口被拒绝；未确认建议不改变正式清单；重复 / 过期决定不会产生额外 Issue 或修改另一版本。身份与存储验证缺口如实列出，不声称已取得操作系统隔离能力。

2. **B2：项目概览、Issue 看板和边界内记录。**

   在 B1 上补齐项目的 Intent / Issue 概览和关联、Issue 详情的“做什么 / 为什么 / 如何验证”、候选方案的收益风险及外部对话结论、用户已决定与尚待决定内容。将待审建议与正式清单区分。

   工具端支持查询和允许范围内追加讨论、备注及 Agent 报告；来源可查，越界请求被拒绝。报告不变成系统观察或人工验收。具体状态展示按实际含义设计，不假造运行中、CI 已通过等 Runtime 状态。

   完成标准：用户可从概览追溯到原意图、当前单元、方案决定及验证计划；同一条记录在 CLI 与界面一致；不在范围内的对象或操作不能因目标相关而写入。

3. **B3：关键变更、范围更新与差异审查。**

   扩展到已确认 Intent 的修订、Issue 目标 / 范围 / 验收条件变更及方案选择。新交付单元先提待审建议，解释变动及理由；原记录在未确认时保持有效。

   Intent 修订保留先商讨、再明确授权的要求，界面决定不代替此前所需讨论。用户只批准其实际审过的内容；如涉及本次工作范围变化，明确展示并由用户决定，不能暗中扩大工具或执行权限。

   完成标准：差异、理由、关联对象和用户决定可追溯；旧版本、提案被替换、重复决定和存储失败都有真实处理结果；相关记录与范围只按用户明确接受的内容更新。

4. **B4：故障路径、端到端验证与试用交付。**

   接入适用的自动检查，完成关键端到端场景和实际浏览器交互验证，整理安装 / 启动 / CLI 使用说明与剩余限制。不为测试通过改变已确认意图或跳过错误路径。

   完成标准：通过下表中与实际实现相符的检查；用户在看板中核对概览、原意图、方案依据、变更差异和决定结果。形成可试用交付材料，但不由测试通过自动宣称产品有效性改善或 E1–E4 全部成立。

## 必须验证的行为

| 检查 | 具体判断 |
| --- | --- |
| 待审与正式清单 | CLI 提交新增建议后原清单不变；用户确认 / 拒绝 / 退回产生各自真实结果 |
| 人端与工具端 | 工具身份不能批准；伪造身份字段或绕开 CLI 直接请求也不能获得人端权限 |
| 已划定边界 | 范围内允许的普通记录可保存，跨项目 / Intent / Issue 或不允许操作被拒绝 |
| 意图与方案 | Agent 建议和摘要不自动变成用户决定；关键变更有差异、理由和适用版本 |
| 并发与重复 | 旧版本决定被识别；相同请求重试不产生重复记录，冲突不静默覆盖 |
| 事务与恢复 | 模拟存储失败不能留下半个正式 Issue 或无对应决定的生效记录；重启后读取一致 |
| 页面行为 | 空、加载、读取失败、部分结果分别显示；输入保存失败保留内容，键盘可完成主要操作 |
| 真实运行边界 | 看板不伪造工具执行、CI、Git 交付或人工验收；PR 四段模板只作为既有文本规范 |

执行时增加与上述行为对应的测试及检查命令；当前 npm run check 已覆盖全端 / 测试类型及非浏览器行为，浏览器交互另运行 npm run test:e2e。现有 V12、V13、V15、V16 是先行看板的重要依据；V14 为交付文本要求，真实工具 / CI 相关场景仍后置。
