# 领域治理与权威事实

为了让人理解方案并核对交付是否仍对应原始意图，需要把问题、方案理由、许可、执行、证据与判断分别记录，同时保留它们之间的对应关系。本文件是领域语义、G0–G4 和事实源边界的主要规范；运行职责见[架构](architecture.md)，技术准入见[验证](validation.md)。

## Harness 候选与跨会话继承（2026-10-26）

用户要求 Harness 与现有 JSON 合同配合，关键长期信息和当前进度可在跨会话时读取。首个切片只提出归属一个 Requirement 的 open_question / assumption，以 unknown / proposed 保存候选；保留候选和正式应用具有不同效力。完整对话是短期上下文，本轮最多使用 600 字的短问题，长期正式内容及最小出处由人端核对后保存。

运行范围与来源由服务从人端启动及实际记录建立，模型输出不能构造人工决定、授权、可信观察或验收通过。人端应用只追加待核对信息及来源，现有 Intent、Requirement 状态、核查和整体接受不变；不能把应用候选解释为接受其事实真实性。

Run、输入快照、事件、候选及应用回执是执行过程事实，不是第二套可自由编辑的正式需求。跨会话的新 Run 读取当前正式 JSON 和项目修订，未应用候选不自动纳入已保存知识。当前步骤使用 scripted-v1，脚本输出不证明模型理解或真实语义提炼；真实模型接入与最终人工验收继续独立。

## JSON 记录、Requirement 与拆解产物

用户在 2026-10-25 后续讨论中进一步确认：对话作为短期上下文，长期 JSON 提炼关键内容；暂不展开团队协作、业务记录目录或 Git 版本管理。最小出处保留对话 / 消息标识、参考链接和必要短摘录，不长期归档完整 Markdown 对话。

Intent 拆出 Requirements，Requirement 在目标看板中对应 Issue。每个 Requirement 拥有多个按需出现的 Unit / Story / Bolt Plan，子产物唯一归属该 Requirement，其内部可以有依赖；不跨 Requirement 共享归属。依据用户 2026-10-30 确认的决策 SC-005（详见[路线图](json-schema-roadmap.md)），PR 是可选交付关联（支持零个、一个或多个 PR，无 PR 时仍可通过适用的产物、客观证据与人工接受完成整体验收），子产物不各自挂载独立 PR，亦不因多 PR 改变归属；这明确替代了 2026-10-25 形成的历史规则（原规定“一个 Requirement 对应一个最终 PR”）。分层合同由用户在反向对话中明确选择，不采用一层通用子任务替代。当前代码与 Schema 仍处于单 PR 阶段，属于已知实现差距，安排在 P06 改造。

子产物分别记录计划与实际的“做什么 / 做了什么、为什么、预期 / 实际影响、如何验证及证据”。各产物通过不能替代 Requirement 整体核对；若存在关联 PR，在 Hub 的 Requirement 和 GitHub PR 中对应表达。UI 仍待后续适配，B1–B3 的旧交付 Issue 和父子字段不自动成为新模型。

当前仅实现独立 JSON Schema / 关系校验，见[合同说明](json-schema-contract.md)。human_confirmed、accepted 或核查 passed 是记录中的陈述；离线校验只能检查相应结构 / 引用条件，不能验证人工身份、批准真实工作或鉴定证据真实性。既有正式人端决定与工具边界继续有效，不能通过导入 JSON 绕过。

## 核心对象

| 对象 | 正式含义与必要内容 | 边界 |
| --- | --- | --- |
| Intent | 用户确认的意图，是目标与预期行为的唯一事实源，表达源头问题、总体目标和边界 | 修改须先商讨并获用户明确授权；下层完成不自动构成整体意图验收 |
| Requirement / Issue | Intent 拆解后的需求及可验证交付边界（依 SC-005 可选关联 0..N 个 PR，替代历史强制单 PR 绑定）；包含目标、理由、收益风险、范围与整体验收条件 | 内部 Unit / Story / Bolt Plan 分别提供验收依据，唯一归属本需求，不各自提 PR；不把每次操作都机械拆成 Issue |
| Grant | 人工批准的任务级授权，覆盖目标、约束、工作范围、必要工具能力、预算和验收条件 | 不是 Sandbox 能力证明；重大变化需重新评估授权 |
| Activity | AIDLC 的活动单位 | 不等于 Issue 或 Run；不据此发明完整工作流 |
| Run | 一次有边界、有预算、可追溯的实际工作执行 | 首版只允许一个主要写入 Run；可在有效授权下跨多个 Activity |
| Evidence | 真实观察、测试结果、交付内容及结论依据 | 模型自述不能成为唯一执行证据 |
| Review | 针对确定交付版本的审查对象 | Run 完成和模型完成声明不等于人工最终验收 |
| Decision | 对重要变化与关键判断的正式记录，保留决定、依据和适用边界 | 涉及需人工裁决的事项时，不能由 Agent 单方产生审批效力 |

Session 是可重建的运行上下文，不承担正式授权与审批的权威事实职责。

## 对话前置与意图确认

为避免模糊任务直接变成实现、业务规则和责任由模型自行补定，Hub 在正式交付拆分与执行前先通过对话形成双方明确的意图。入口可以是用户的初步想法或已有材料；Hub 结合现有上下文，围绕关键歧义追问、解释选项并核对理解。

参考依据已按用户更正校准为《深入理解 AI-DLC》[第 2 章“人的判断”](../references/aidlc-book-reference/aidlc-book-baojun/book/chapters/ch02-human-judgment.md)：先明确 Intent、Boundary、Non-delegable Judgment、Human Checkpoint、Accountability，由 AI 提议和暴露问题、人作关键判断、工程记录决定；章节明确讨论反向对话。可执行计划的形成另见[第 3 章 Inception](../references/aidlc-book-reference/aidlc-book-baojun/book/chapters/ch03-inception.md)。此前对旧书“第二章上下文工程”和“第五章 Coding Agent 整体流程”的引用失效，详见[纠偏记录](reference-correction-plan.md)。本节仍以用户明确确认的意图与责任为规范，不把上游方法当作本项目已有实现或执行许可。

对话应使以下内容明确到足以判断和执行的程度；它们是需要达成的理解，不是要求用户一次填完的表单：

| 内容 | 要澄清的问题 |
| --- | --- |
| 意图与结果 | 源头问题是什么，为什么值得解决，预期实际结果是什么 |
| 范围与约束 | 本次交付的边界、明确不做的内容、业务规则和必要约束是什么 |
| 方案与取舍 | 为什么选择该方案，有何收益、风险和需要用户判断的取舍 |
| 责任与权限 | 用户决定目标、业务取舍、意图修改和最终验收；Hub 组织流程、授权检查、记录、提交推送与 CI 反馈；Agent 在获准范围内分析和实施，不自行批准意图或验收 |
| 验证与交付 | 用哪些实际场景和证据判断完成，如何说明影响，哪些结果由 CI 检查、哪些须用户实际验收 |

Hub 应用清楚的语言复述候选 Intent 与责任分工，分别标明已确认内容、建议和未决问题。候选草案、模型复述和对话摘要都不自动成为正式意图；用户确认后，才作为目标与预期行为的唯一事实源，并据此进入正式交付拆分。Intent 确认不自动授予所有工具和 Git 权限，执行仍须有效 Grant 与已验证能力。

不固定对话轮数，不要求重复回答仍适用的已确认事项。关键问题未明确时，只在已有授权内继续澄清或调查，不推进依赖该结论的交付工作。已有明确 Intent 可复用，发现影响目标或责任的新歧义时再回到对话；意图修改按下一节处理。

已确认意图、责任、约束和判断依据应能在后续上下文中被准确获得。摘要和上下文压缩不得改变这些内容的含义或制造授权；关键条件无法从摘要确定时，回查正式记录。具体存储、消息布局和压缩实现尚未选定。

## 先理解再推进

2026-10-25 用户在多轮反向对话后明确确认：AgentHub 要帮助使用者从源头问题出发，理解为什么需要改动、核心逻辑如何产生预期结果，并用适用证据客观核对实际影响。它应使“源头问题 → 必须满足的条件 → 备选方案与取舍 → 核心实现机制 → 实际影响 → 验收证据”可以被理解和追溯。

理解与推进冲突时，先理解，再推进。核心逻辑同时包含业务逻辑和关键技术机制，要求深入理解，不能把“说明看起来合理”当作理解已完成。理解是否充分由用户判断；用户尚未理解时，不推进依赖该核心判断的正式实现。仍适用的已有理解、决定和授权可以复用；这不要求每个普通操作重新审批。

Agent 应解释影响范围、备选方案的收益与风险、推荐依据及未知项，结合具体行为和因果关系说明业务与技术机制。需要补足知识时，提供与当前问题对应的参考链接及适用版本；关键假设无法靠解释确定时，可提出有范围、预期、方法、预算和停止条件的小实验，由适用任务授权决定能否执行。链接、实验建议或阅读时长本身不证明用户理解，实验也不能因“有助理解”而自动获得许可。

反向对话用于发现理解缺口和澄清取舍；用户的追问、尚未理解的内容与未验证假设应保留，不能由摘要静默消除。不设模型判定的知识分数或强制测验，不因用户未继续追问就推定已理解。用户明确理解并作出方案决定、正式授权、实际执行与最终验收具有不同效力；记录系统不得把它们合并为一个自动“通过”。

此前第一版计划在没有内置 LLM / 自有 Harness 时先承接外部 Agent 的材料；用户随后明确调整建设次序：先建立记录体系及自有 Harness，再接入 LLM 推进并验证解释、审查和工作执行。材料、候选、人工决定与证据的语义仍有效，详见[当前建设次序](#记录体系与-harness-建设次序)。当前 B1–B3 只有其中部分记录与审批能力，不证明上述目标全部实现。外部 Agent 是否停止执行不能由 Hub 的待决定状态保证；后续自有 Harness 的阻断与恢复能力须另行实现和验证。

证据核对系统行为与实际结果，用户判断自身理解；两者相互支持但不能替代。具体产品验证见[理解与决策闭环验证](validation.md#理解与决策闭环的验证要求)，第一版候选交互见[架构](architecture.md#看板版本的最小交付)。

## 记录体系与 Harness 建设次序

2026-10-25 用户明确调整当前目标：先建立 AgentHub 专属的 Markdown + JSON Schema 记录体系，并建设自有 Harness。结构化 JSON 实例后续融入类似 Multica 的分状态 Issue 看板，详情分块与合同对应。此前先完善决策走读 / 审阅交互再推进 Harness 的建议次序被替代；先理解再推进的产品原则与人工责任继续有效。

Markdown 保存自然语言和解释，JSON 实例保存对象与适用事实，JSON Schema 定义合同；看板和模型上下文按版本从正式数据投影，不分别自由改写同一份决定。状态迁移仍须满足相关版本、权限与人工判断，不能因移动卡片而获得授权或验收效力。书籍工件关系见[Inception](#inception-工件与-standards)，具体候选设计见[建设计划](records-and-harness-plan.md)。

LLM 参与的解释、审查和语义验证在基础及模型接入后进行；Schema、引用、状态、权限等确定性检查可在接入前验证。模型输出是待检查的提议，不因符合 Schema 就证明符合 Intent。最终实际验收仍由用户负责；骨架、测试替身和模拟事件不能替代真实模型 / 工具证据。

## 工具写入与人工检查

2026-10-23 用户明确偏好类似 Multica 的交互：提供 CLI 或其他工具完成写入，再由用户检查与审批。已确认的是工具写入与人工判断的职责，不表示已选定具体协议、已建立可用 CLI 或已批准全部写入自动生效。

外部 Agent 可以通过获准工具提交 Intent / Issue、方案、验证计划或变更建议；Hub 应呈现内容、来源、关联对象及修改前后，供用户判断。正式确认、审批及已确认 Intent 的修改仍按本文件既有规则处理，工具不能伪造用户决定。数据写入成功和人工批准是两种不同事实。

建议待审变更指向明确对象及所基于的版本，避免用户批准后变更内容又被静默替换；重复提交、旧版本变更和写入失败应明确处理。以上为实现方向，真实身份、权限、冲突与保护机制仍待设计和验证。

用户已选择“关键内容审批、普通记录可直接保存”，前提是操作处于用户划定的有效边界内。这是两个同时适用的条件：处于边界内不意味着关键内容可以免审批；属于普通记录也不意味着可以跨边界写入。

边界内的讨论、备注和进度报告可按允许范围保存，并标明来源；Agent 报告不能自动变成已验证结果或人工验收。Intent 确认与修改、Issue 的目标 / 范围 / 验收条件、方案选择等关键内容仍需用户判断。超出边界的变更只能作为请求提出，不据此修改范围外的正式记录；边界缺失或无法判断时，先澄清，不由 Agent 自行扩张解释。

B2 将普通记录边界实现为人端发放令牌时明确选择当前 Intent、具体正式 Issue 和允许记录类型；见下节。新增已确认清单之外的交付单元，已按下节明确为先提待审建议，再由用户决定是否纳入正式计划与工作范围。工具写入权限也不能被解释为实际 Runtime 的代码、Git 或其他执行授权。

## 新增交付单元与变更审查

用户明确选择：在已确认 Intent 和交付 Issue 清单之外发现需要新增子 Issue 时，Agent 先提交待审建议，由用户知道变动内容及理由并作出决定。即使建议与原 Intent 一致，也不能据此直接加入正式交付计划或自动扩大获准推进的范围。

Agent 应为用户准备变更说明，至少明确“变动了什么、为什么要变动”。为支持既有方案判断和验证要求，交互还应呈现关联 Intent、受影响 Issue、必要的前后差异、收益风险及拟验证方式；这些信息用于判断，不要求用户重新填写已知内容。

用户可确认、退回补充或拒绝建议。未确认时，原正式计划与工作边界保持有效；待审建议本身不是新增工作授权。确认后仅在用户明确接受的范围内更新计划，相关 Grant 与实际执行能力仍须分别核查；不能把确认新增 Issue 解释为所有工具、Git 或 Runtime 权限的自动扩大。

建议界面将待审建议与正式 Issue 清单区分，显示变更依据及当前处理结果，并绑定被审内容的版本。具体视觉布局、版本冲突和防篡改机制仍待实现与验证；本规则不表示审批保护已经存在。

## 看板同步与审阅版本

用户明确要求工具 / Agent 新增内容后，已打开的页面主动更新，避免依赖手动刷新。同步更新只反映已保存事实，不扩大正式计划、工具范围或执行授权，不代替人工决定。

更新应保留当前查看位置和未提交输入，不自动选择或批准新增提案。若所审提案、Intent 或正式计划版本已改变，应明确提示并暂停原审阅提交；用户核对最新内容后才能继续，提交仍须绑定被审版本，后端再次检查冲突。只新增待审建议不改变正式计划，不要求无关审阅重复确认。

断线或读取失败时保留上次成功内容并明确标示，恢复后重新读取，不把旧快照显示为已获最新确认。当前接口内的同步与版本检查不证明宿主保护或可信审批，工程事实见[状态文档](project-status.md#b1-自动同步修复2026-10-23)。

## 决定说明与处理结果

决定说明应服务于理解和后续行动，避免用户在接受现有提案时被迫重复填写已呈现的方案依据。用户已明确沿用批准、退回、拒绝三种决定，不新增暂缓状态：

| 决定 | 说明要求 | 处理含义 |
| --- | --- | --- |
| 批准纳入 | 补充说明选填，可不写或仅补充判断 | 接受所审版本的提案，按原边界纳入正式计划 |
| 退回补充 | 必填非空理由，说明需要补充或调整的内容 | 当前提案未纳入计划，供后续讨论与修订 |
| 拒绝 | 必填非空理由，说明不纳入的原因 | 当前提案不纳入计划，保留决定与理由 |

批准时仍记录决定主体、动作、被审版本与时间；没有补充说明时如实保存为空，界面显示“未补充说明”，不得自动代填“合理”“同意”等人工未写的理由，也不得删除已有历史理由。提案本身的变动理由、收益风险和验证方式仍须完整，不能因批准备注选填而省略。

前后端应执行一致规则。退回 / 拒绝中的纯空白不算有效理由；批准中的纯空白按未补充处理。切换决定时保留各自草稿，不能把批准备注自动当作退回 / 拒绝原因；只有明确提交才保存相应决定。

补充说明用于解释对当前提案的判断；如果需要改变目标、范围、方案或验收条件，应先退回调整并重新审阅，不通过批准备注隐含修改被审内容。上述规则不改变人工确认、版本绑定、工具范围及实际执行权限。

## 意图的唯一事实源与变更

经用户确认的 Intent 是“要解决什么问题、预期得到什么结果”的唯一规范事实源。Requirement / Issue、其拆解产物、方案、PR、测试与验收条件都应追溯到适用的 Intent，不能单方面重新定义其含义。本文件不预选 Intent 的文件、数据库或具体存储结构。

意图修改必须先与用户商讨，说明已有证据、拟修改内容、理由和影响；只有用户明确授权修改后，才能在授权范围内更新。讨论、模型建议、实现困难或 CI 失败本身都不构成放权。应保留修改前后内容、理由、人工授权及适用边界，并重新核查相关 Issue、PR、Grant 和 Evidence 的适用性。

实际结果偏离 Intent 时，记录偏差并按原意图修复；确需改变意图时，先走上述商讨与授权过程。不能通过静默改写父 Issue、子 Issue、预期结果或验收标准，把语义偏移包装成符合要求。方案与实现的普通调整仍按有效 Grant 执行，但不得借此改变 Intent。

Intent 决定目标和预期；实际代码、工具执行和远程结果仍须依据各自的事实来源观察。已确认的意图不证明操作发生，也不能替代 Git、CI 或实际运行证据。具体事实职责见[权威事实源](#权威事实源与持久化边界)。

## Intent、交付单元与语义对应

当前关系为 Intent → Requirements（看板 Issue）→ 同需求内按需出现的 Unit / Story / Bolt Plan。依据用户 2026-10-30 确认的决策 SC-005（详见[路线图](json-schema-roadmap.md)），PR 是可选交付关联（支持 0..N 个 PR，无 PR 时仍可通过适用产物、客观证据与人工接受完成整体验收），替代了历史单 PR 规则。拆分解释子产物解决什么问题、为什么需要独立核验及如何验证；子产物唯一归属该需求，不要求各自提 PR，不以固定层数、数量或无限细化为目标。旧父子 Issue 的实际数据保留，映射另行处理。当前实现处于单 PR 阶段，属于已知实现差距，安排在 P06 改造。

推进前，Agent 应围绕交付单元的候选方案、选择依据、收益、风险与验证方式，与用户进行反向对话，最终由用户决定采用的方案；Hub 记录讨论结论与该决定。已批准方案与授权内的普通实施细节不因此逐步增加人工审批。看板版本先在外部 Agent 中讨论，再在 Hub 中记录，不把模型建议、外部对话摘要或手工录入自动当成用户已确认。父子关系本身不授予执行权限；普通实施步骤也不因此变成独立的人工审批节点。

Issue 与交付说明共同回答以下问题，保留预期与事实的区别：

| 关注点 | Issue 中的预期 | PR / Review 中的实际情况 |
| --- | --- | --- |
| What | 要解决的源头问题、交付边界与验收条件 | 实际完成的改动及其对应的 Issue |
| Why | 方案理由、预期收益、风险和关键取舍 | 实际采用的方案及与原方案不同之处的理由、相关 Decision |
| Result / Evidence | 预期结果及准备如何验证 | 确定版本的 CI 与实际运行结果、证据、偏差和未验证项 |

新增信息可以形成意图修订提案；修订生效必须满足[意图变更规则](#意图的唯一事实源与变更)，并按授权变化与 G3 处理。PR / Review 还应明确“本次修改产生了什么影响、有什么结果”，供用户与实际运行核对。具体 UI、文案模板和自动同步机制尚未选定。

## Inception 工件与 Standards

本节按新书原文校准术语，说明后续建模必须保留的含义；不表示这些对象已经实现，也不把参考方法自动升级为获准实施的架构方案。原文为[第 3 章](../references/aidlc-book-reference/aidlc-book-baojun/book/chapters/ch03-inception.md)：

Intent → Requirements → System Context → Units → Stories → Bolt Plan → Human Checkpoints。

这是一条形成可执行计划的工件链，不要求把所有对象塞进同一种父子树。Requirements 描述功能与非功能要求；System Context 记录实际环境、外部依赖和系统边界；Unit 划定可独立交付的能力；Story 表达用户价值、需求引用与可判定验收；Bolt Plan 在小时到天级批次中安排 Story、阶段、产物与检查点。Human Checkpoint 指明何时、由谁、依据什么作出关键判断，不是每个细小动作都要审批。

[第 4 章](../references/aidlc-book-reference/aidlc-book-baojun/book/chapters/ch04-memory-bank-standards.md)中的 Standards 是贯穿这些工件和执行的工程约束，应明确适用范围、版本和检查方式，不是 Story 或 Bolt 之后的末级任务。后续设计还需区分 Standards、Story 的预期验收条件与 Evidence 的实际观察，不把三者混为“标准已通过”。

当前 Intent / 父 Issue 与交付 Issue / 子 Issue 的产品表达继续有效；现有 Issue 字段和父子引用没有独立实现 Requirement、Unit、Story、Bolt 或 Standard。不得自动断言“父 Issue 就是 Unit、子 Issue 就是 Story”；历史 B1–B4 也只是编码计划编号。实际映射须说明含义、版本、关系与迁移影响，供用户理解后决定。拆分深度服务于问题边界、风险和验证，不照搬书中练习的固定数量或强制填满每一层。

Markdown 可保存原始对话、解释和方案取舍；结构化记录可保存确定对象、版本与引用；Schema 定义其可接受结构。对话摘要不是批准，JSON 中自填的 approved 或验收 passed 也不能获得正式效力。正式内容与审批事实仍通过本文件既有规则产生，界面和导出只是相应事实的表达。候选结构、校验职责和实施次序见[参考纠偏与推进计划](reference-correction-plan.md)。

## PR 四段式说明与人工证据

2026-10-23 用户明确 PR 按以下结构编写，并由用户附加截图等证据。结构服务于“理解改动并验证是否符合最初意图”，不决定谁实际创建 PR 或授予远程操作权限。

| 固定段落 | 需要说明的内容 |
| --- | --- |
| 做了什么 | 关联 Intent / Issue，实际改动、影响范围与未覆盖内容 |
| 为什么这么做 | 原问题、备选方案、收益与风险，以及反向对话后的用户方案决定 |
| 如何验证 | 对应意图的场景与预期、检查方法；实际运行时关联环境、版本和观察来源 |
| 结果怎么样 | 实际检查和运行结果、与预期的偏差、未验证项；用户补充截图等人工证据及其说明 |

Hub 可整理真实日志、检查或 CI 观察；用户负责补充截图等人工证据。截图等材料应说明对应场景和交付版本，未知信息保持未知；截图存在本身不证明所有验收条件成立。未运行或未观察到的结果不得填成通过，模型也不能代替用户附加或确认真实观察。

[PR 写作模板](templates/pr-description.md)只提供文本格式，不是自动创建器、附件上传实现或验收记录。看板版本是否内置 PR 编辑和附件入口尚未确认；PR 创建方式、时机和 Merge 责任继续保留为后续取舍。

## 任务授权与变化

Grant 使 Agent 能够在人工已批准的任务范围内自主推进，而无需由模型临时解释出新权限。实际可执行范围同时受**当前有效 Grant 与已验证执行能力**约束，任一不足都不能据此放行操作。

任务目标、权限、约束、验收标准及交付边界等重大变化需要重新评估授权。授权内的普通组织调整可以自动留痕；重要变化和关键决策交由人工裁决。

Rules、AGENTS.md、Skills、工具返回及模型上下文不能自行扩大正式授权。授权失效或撤销后，不得继续依赖旧 Grant 执行；恢复也必须重新核查当前有效授权。

## Evidence 与 Review

Evidence 必须分别判断三个维度，不能以其中一项替代另外两项：

| 维度 | 核查的问题 |
| --- | --- |
| Integrity | 来源与记录是否真实、可信 |
| Applicability | 是否适用于当前对象和版本 |
| Sufficiency | 对当前结论是否充分 |

真实工具观察、测试结果和交付内容应支持结论；模型解释可以补充分析，但不能代替真实执行依据。独立观察与实验判定见[验证文档](validation.md)。

Review 应包含：

- **做了什么**：实际改动及影响范围。
- **为什么这么做**：问题、方案取舍和用户决定。
- **如何验证**：对应意图的场景、预期与检查方式。
- **结果怎么样**：实际结果、影响、风险及与 Issue 预期的差异；用户补充截图等证据。
- **Commit / Code Identity**：明确被审查的交付版本。
- **Evidence**：适用于该版本的 CI 结果、实际运行观察及其他必要证据；缺失或结果未知须说明。
- 未验证事项与剩余风险。

交付内容或版本变化时，应重新核查 Evidence 适用性与 Review 对象；旧版本的审查不能自动成为新版本的验收。

## G0–G4 与人工责任

这些 Gate 表达研发治理语义；实验、实现和可信晋升的四层准入另见[验证文档](validation.md#四层准入与可信晋升)。

| Gate | 语义 | 检查及人工责任 |
| --- | --- | --- |
| G0 | Issue 准入 | 确认问题独立、可验证，目标和结束条件足以进入后续授权 |
| G1 | 任务 Grant | 人先理解方案理由、收益和风险，再批准任务目标、约束、范围、能力、预算与验收条件 |
| G2 | 执行活动与证据适用性检查 | 核查 Activity 是否处于有效授权内、Evidence 是否适用；授权内普通组织调整可自动留痕，重要变化转 G3 |
| G3 | 意图修改、重要变化与关键决策 | 意图修改先与用户商讨并获明确授权；由人工裁决重要权限、验收、交付边界变化及重大架构改道 |
| G4 | 最终交付验收 | 由人工针对确定交付版本、Review、Evidence 与剩余风险作出验收判断 |

CI/CD 和实际运行是两道交付质量门禁，不替代这里的 G0–G4，也不替代技术实验与可信晋升的准入。

人负责关键决策、权限扩大、可信组件晋升与最终验收。Agent 的“任务完成”、Run 结束或工具成功返回均不能替代上述责任。

## Git 交付边界

用户于 2026-10-30 确认新基线 SC-005（详见[路线图](json-schema-roadmap.md)），明确废除历史“一个 Requirement 对应一个最终 PR”的规则：PR 成为可选交付关联（0..N）；无仓库或无 PR 时，仍可通过适用产物、客观证据与人工接受完成验收；内部多个拆解产物分别验证后汇总交付，子产物唯一归属该需求，不单独对应 PR，亦不因多 PR 改变归属。Requirement 整体核对和最终人工验收仍独立于子产物的技术通过。当前实现仍为单 PR 约束，属于待 P06 改造的已知差距。

已确认的交付责任是：Hub 提交前检查实际改动与本地测试，确认本地测试通过后在获准范围内提交、推送，并查看对应版本的流水线信息；用户介入最终实际运行验收，核对实际影响、结果及 Issue / PR 说明是否符合 Intent。失败时在适用授权和原意图内返工，不能擅自降低验收条件。

先交付 Intent / Issue 看板、再接入 Runtime 的顺序已确认。原本地 Commit / Review 链路保留为技术验证切片；PR 四段式说明和人工截图等证据责任已明确，PR 创建方式、运行场景和 Merge 的产品责任仍待细化。完整交付流程见[验证契约](validation.md#两道交付门禁)。

获准本地 Commit 经可信 Git Broker 完成。Hub 编排提交推送的产品责任不等于 Agent 获得任意 Git 权限；Push、PR、Merge、Release 不包含在仅有本地 Commit 的授权内，须由适用 Grant 明确覆盖，并验证凭据、网络和副作用边界。现有 Broker 的本地职责不自动扩展为远程实现。本轮文档调整也未获得实际 Git 写操作授权。

## 权威事实源与持久化边界

为了避免请求、记录和外部结果互相冒充，应按事实性质核对来源。

| 来源 | 权威范围 | 不能由它推导的结论 |
| --- | --- | --- |
| 已确认 Intent（由 Hub Protected Records 保护） | 目标与预期行为的唯一规范依据，变更依赖用户明确授权 | 不能证明代码、工具操作或远程交付已实际发生 |
| Local Git | 代码内容、提交历史和实际仓库状态 | Commit 成功不代表 Hub 已正确记录或人工已验收 |
| Hub Protected Records | Intent 及其修改授权、Issue、Grant、重要决策、人工 Review 和可信验收等正式领域事实 | 请求已记录不代表 Git 或其他工具真实完成 |
| Tool Execution Observations | 工具真实执行、日志和外部副作用的观察来源 | 执行观察不自动构成授权、充分证据或验收 |
| Remote GitHub / CI | 实际远程提交、PR、Merge 和 CI 运行事实，分别核查目标版本与结果 | 本地记录或 Commit 不代表远程操作已经发生 |

中断和恢复时必须核查实际外部副作用，区分已知完成、已知未完成与结果未知，再核查授权和 Evidence 的当前适用性。不得用请求记录或模型叙述填补未知结果。

持久化需要满足受保护写入、授权失效、备份恢复和敏感信息清理要求。备份、会话重建或恢复流程不能使已失效授权重新生效，也不能绕过可信写入边界。此处不预选数据库、事件溯源系统或表结构；具体机制和恢复能力仍待[技术验证](validation.md)。

## B2 普通记录的适用边界

B2 记录用于保留过程信息，分为 discussion（讨论摘要）、note（备注）、agent_report（Agent 报告）。每条关联当前 Intent，或其已有正式 Issue，同时保存写入时的 Intent 版本。主体与来源身份从已认证通路生成；外部来源描述由记录者提供，不因出现链接或对话标题而成为可信证据。

人端发放工具令牌时，明确勾选当前 Intent / 具体正式 Issue，以及允许的记录类型；缺少对象或类型不能授予追加能力。未启用追加和历史令牌保持原权限。新增子 Issue 不自动加入父 Issue 的记录授权，撤销后不可继续调用。记录可直接追加的判断不改变关键内容仍需审批的规则。

记录只能追加原文，后续更正另附一条；不能在这里改 Intent、Issue 的目标 / 边界 / 方案 / 验证，不能指定人工批准或可信验收状态。讨论摘要中的“用户同意”和报告中的“测试通过”仍是记录者陈述，正式方案及决定从原提案与人端决定追溯。人端记录来源也不等于完成实际运行验收。

本节细化 D8.6 的工程表示，不授予实际模型、工具、Git 或 Runtime 权限。当前身份和记录保护的实际限制见[安全](security.md#b2-记录权限检查)，验证证据见[工程状态](project-status.md#b2-概览与边界内记录2026-10-24)。

## B3 关键修订与历史

关键变更先形成不可原地替换的候选，包含对象、对象 / Intent / 计划基准版本、服务读取的原内容、预期完整内容、理由和影响。工具需有人端明确授予的 change:propose 及具体对象范围；旧权限不自动扩大。提交成功只保存候选，原意图、正式单元和工具范围保持有效。

人端逐字段审阅前后，决定绑定所审候选及当前 Intent / 计划版本。批准将正式内容、对象版本、计划版本、候选状态和决定在同一事务内保存，并保留原快照；退回 / 拒绝不改正式内容且理由必填，批准说明选填。审批不授予 Runtime 或 Git 权限。基准已变时不可批准；退回后按最新内容另提候选，不靠改编号或版本字段伪装适配。旧候选及原决定始终保留。

Intent 的候选可以用于商讨，不能直接套用普通修订批准。本人完成商讨后，须通过人端独立入口记录结论 / 来源并明确授权该候选；登记不立即改意图。授权变化会改变被审建议版本，最终应用仍需重新核对并批准；可在应用前撤销，不能转移到其他候选。工具不能代为登记、撤销或审批，普通讨论不等于授权。该交互记录人端对商讨的声明，不虚构系统观察到对话过程。

Intent 改变后，派生 Issue 保留原内容与原 Intent 版本并提示重新核对，旧新增提案 / 修订不能直接批准。人工确认对应关系需提交新建议；Issue 内容确实无须变化时，允许通过明确的重新确认修订更新对应版本。旧记录不会被自动改写成与新意图一致。

写入范围调整由本人发放新范围并按需撤销旧令牌，具体新 Issue 不自动加入；批准方案也不会重写范围。当前范围是应用工具权限，正式 Grant 与受控执行仍独立后置。实现及证据见[工程状态](project-status.md#b3-关键变更与差异审查2026-10-25)。


## 正式 JSON 看板的记录变更

正式看板的卡片是 Requirement，可选 Unit / Story / Bolt Plan 归属在其内部；工作状态、实际结果、逐条件核查和人端整体接受分别保存。通用编辑必须说明理由、预览修改前后及关联影响，再由人端明确确认；保存修订号失效时保留草稿并重新核对，不静默覆盖新内容。

修改工作对象的内容后，不再沿用原通过核查；修改已接受需求或其子产物后，当前整体接受失效。旧内容、理由、关联变化与接受留在审计历史，不改写为新版本背书。来源与观察证据采用追加更正。总体接受须独立人端确认，并满足全部子产物和整体条件与适用证据（依 SC-005，关联 PR 为可选交付项，无 PR 时不强制 PR 存在）；记录中的“通过”仍不能代替真实观察或实际用户判断。

旧数据先做迁移预览：每个旧正式 Issue 生成 Requirement 草案，父子关系、原方案 / 风险和批准保留为来源，不自动推断分层或验收。人端确认后另存 JSON，旧业务只读；迁移确认不代表接受新需求，意图新表示另行核对。当前通用编辑不允许改写已确认 Intent 正文。映射见[合同](json-schema-contract.md#现有模型衔接)，操作及未实现部分见[指南](record-board-quickstart.md)。
