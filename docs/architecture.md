# 产品架构与 Runtime 职责

本文件说明已确认的产品职责关系，并记录本次获准初始化的 TypeScript 目录组织；目录不是业务能力或安全隔离的实现证明。本轮未定义业务 API、数据库或界面框架。实现与验证状态以[工程状态](project-status.md)为准，领域对象以[治理](governance.md)为准。

## 为什么需要 Hub 控制层

开发者需要在 Agent 推进前理解方案的理由、收益和风险，并在推进后核对实际结果与原始意图。理解速度落后于执行、Issue 描述与实现发生语义偏移，都会使规范的记录无法支持真实判断。

Hub 因此把任务看板、方案决策和实际执行连接起来：以问题边界组织交付单元，在有效授权内执行，收集真实观察，并让 Issue 中的预期与 PR / Review 中的结果保持对应。Agent 不能仅凭自身判断建立授权、证明真实执行或确认最终交付。

产品交互从用户的想法或已有 Intent 开始，经对话明确意图、责任、边界与验证方式，由用户确认；已有且适用的确认可复用。正式执行入口仍是通过准入的 Issue 和人工批准的有效 Grant；出口是可追溯的实际工作、Evidence 与绑定交付版本的 Review。人工最终验收独立于 Run 完成。对话出口、领域关系和交付说明的具体语义见[治理](governance.md#对话前置与意图确认)，交付门禁见[验证](validation.md)。

## 阶段一首版交互草案（2026-10-23）

用户已确认可以依据现有 Intent 直接开展阶段一，真实项目后续导入验证，不作为首版范围与交互设计的前置条件。本节将既有产品要求整理为可评阅的设计草案；下列功能区域与交互组织是建议，尚未作为已确认布局、实现或冻结的 MVP 范围。

首版闭环候选为：对话澄清 → 用户确认 Intent → 按问题边界组织 Issue 并理解方案 → 有效 Grant 下的单主要写入 Run → 提交前检查与本地测试 → 获准提交推送及 CI 反馈 → 用户实际运行验收。意图变更、授权和事实语义仍以[治理](governance.md)为准；PR 创建方式继续保留为待决定事项。

| 功能区域建议 | 用户需要看懂的信息 | 最小交互建议与出口 |
| --- | --- | --- |
| 对话与澄清 | 源头问题、Hub 当前理解、关键歧义、方案取舍和责任 | 输入或补充想法，回答关键问题、纠正理解；形成候选 Intent，未确认内容保持明确标识 |
| Intent 确认与变更 | 目标、范围、约束、预期行为、责任与验证方式；修订时显示前后差异和原因 | 用户确认或纠正 Intent；需修改已确认意图时先商讨并记录明确授权 |
| Issue 与方案 | 父 Intent、交付单元、拆分理由、方案收益风险及预期证据 | 查看父子 Issue 与目标对应关系，理解或调整方案，再进入明确授权范围的执行 |
| 执行进展 | 当前交付单元、真实动作与结果、预算、等待用户判断的事项和异常 | 查看观察记录与上下文，补充信息、请求暂停或取消；区分已发生、尚未执行与结果未知 |
| 交付与 CI | 明确版本的改动、影响、What / Why / Result、本地测试、远程 CI 结果和未验证项 | 查看差异、日志与证据，跟踪 CI 失败后的返工；PR 说明作为交付材料，具体创建方式待定 |
| 人工验收 | 已确认 Intent、Issue / PR 声明的影响与结果、实际运行观察及偏差 | 用户介入运行验收，记录接受、退回修复或发起意图修改商讨；决定绑定被审版本 |

这些是信息与操作责任，不要求建立六个独立页面，也不定义看板列、状态枚举或数据库结构。建议最小呈现优先满足三件事：随时找到已确认意图及方案依据、看清实际执行发生了什么、对照证据完成最终判断。页面组合和信息展开方式通过草案评阅继续收敛。

本阶段可用角色走读和明确标注的示例检查信息是否足够，不声称工具、CI 或真实项目已运行。首版候选优先覆盖既有的云端模型、自有 Harness、单主要写入 Run 和上述闭环；本地辅助模型、已有 Agent 适配及更广的平台能力按既定优先级后置。具体实现依赖仍须技术验证与实现准入。

## TypeScript 工程组织

2026-10-23 用户授权初始化 TypeScript 工程。先用单包 Node.js + TypeScript / ESM 提供可检查、可编译、可启动的最小入口，避免在产品边界尚未冻结时同时引入界面、服务框架、数据库或工作区管理工具。这些是本次骨架的工程组织选择，不是用户已确认的最终平台或进程架构。

| 路径 | 后续代码职责 | 依赖与边界 |
| --- | --- | --- |
| src/index.ts | 组合各入口与适配；当前只输出骨架状态 | 不在此堆积领域规则、自动模型调用或工具执行 |
| src/domain/ | Intent、Issue、Grant、Evidence、Review 等语义与不变量 | 只依赖自身和纯语言能力，不依赖应用层、Node.js I/O 或外部框架 |
| src/application/ | 对话确认、交付组织、授权与验收等用例协调 | 依赖 domain；外部能力通过所需接口注入，接口按使用侧职责定义 |
| src/harness/ | 自有模型循环、上下文和工具建议处理 | 依赖 domain 及必要应用接口；不得直接提供绕过授权的执行入口 |
| src/infrastructure/ | 模型、持久化、工具执行、Git / CI 等外部适配 | 实现使用侧接口；真实能力的启用仍取决于授权、验证和可信晋升 |
| src/presentation/ | 后续 CLI / UI 输入输出与用户操作 | 通过应用用例进入，不直接修改正式记录或调用高权限适配 |
| tests/ | 后续领域与用例测试、适配集成验证 | 按实际行为建立；本次仅占位，不虚构测试通过 |
| references/ | 两个上游仓库的参考资料 | 排除在项目编译之外；复用前仍需检查来源、许可、语义与实际依赖 |

当前只有骨架入口，其他源码目录和 tests 只有 .gitkeep；没有预先建立领域类型、状态机、模型接口、数据库 Schema 或工具执行器。依赖方向是开发约定，尚未通过静态规则自动强制。目录、TypeScript 的 private 或接口注入均不能代替进程、文件、网络、凭据和可信记录的真实保护；安全机制仍以[安全文档](security.md)和[技术验证](validation.md)为准。

## 三种运行模式与优先级

为兼顾运行过程的掌控与不同模型来源，产品规划三种模式。它们是目标，不代表已有适配或已验证能力。

| 模式 | Hub 的职责 | 优先级与待验证边界 |
| --- | --- | --- |
| 云端模型 + Hub 自有 Harness | 由 Hub 组织上下文、调用模型、检查执行条件并反馈工具结果 | 第一版优先；既有 DeepSeek Loop 为技术起点，本轮未重新指定模型或服务商 |
| 本地模型 + Hub 自有 Harness | 使用同一治理语义组织本地推理及结果使用 | 后续可先承担小型 Reviewer 或文档总结，考虑本机算力限制；不替代人工最终验收 |
| 已有 Agent + Hub 约束 | 组织任务、观察执行，并通过实际可用的接口施加约束 | 后续方向；需证明跨 Agent 操作是否能绕过 Hub，不把看板记录等同于运行时控制 |

自有 Harness 允许 Hub 直接设计运行循环，其安全效果仍须真实验证。接入不同模式时，应说明实际可见、可控和不可控的部分；当前仅有上述 TypeScript 工程基线，未确定模型适配 API、产品界面技术栈或调度机制。

## 职责与信任边界

下列名称表示架构职责，不代表已有同名实现文件或进程。

| 角色或组件 | 承担的责任 | 必须遵守的边界 |
| --- | --- | --- |
| 人 | 理解方案的理由、收益和风险；商讨并授权意图修改；批准任务授权、可信晋升并介入最终实际运行验收 | 不将模型完成声明视为人工裁决 |
| Hub 控制层 | 以已确认 Intent 对齐 Issue、方案与交付事实，组织提交前检查、提交推送、CI 反馈及人工验收材料，维护授权、预算与恢复 | 正式记录和秘密不能暴露给 Agent 任意写入 |
| DeepSeek Agent Loop | 首版由 Hub 自有 Loop 组织上下文、模型调用、工具建议和结果反馈 | 模型输出只是建议；每次实际执行受当前授权和能力约束 |
| Agent | 分析任务、提出操作并推进获准工作 | 执行进程不可信，不能控制授权或可信组件晋升 |
| Tool Executor | 将获准操作转化为真实执行，收集结果和副作用观察 | 负责执行控制，不能将建议直接视为许可；底层机制须验证 |
| Sandbox | 候选的受限进程执行边界 | 机制安全性和适用环境待 X1 证明，名称不代表安全 |
| Trusted Git Broker | 受限修改 Git 管理状态并完成获准本地 Commit | 不提供任意高权限 Git 命令转发，候选实现须经验证和晋升 |

Agent 可以直接修改授权工作文件；Git 管理状态的受限修改和本地 Commit 交由可信 Git Broker。具体保护要求见[安全文档](security.md)，不在本文件预选具体进程拆分或存储实现。

## Hub 自有 DeepSeek Loop

为使自主执行始终处于有效授权内，Hub 应完成以下闭环：

1. 读取用户已确认的 Intent 及其适用修改记录、派生 Issue、已确认方案、有效 Grant 和 Run 状态，确定交付单元、Activity、预算与可用能力；方案、收益和风险尚需人工判断时先呈现，不能由模型自行改写 Intent。
2. 组装包含适用 Intent、责任、约束、决策依据与真实观察的上下文，区分可信领域事实与不可信指令、项目内容和工具返回；摘要不替代正式确认或授权。
3. 调用模型，接收分析与工具操作建议。
4. 在实际执行前检查当前 Grant、能力准入和执行环境；建议本身不授予权限。
5. 通过受控执行能力完成获准操作，收集真实结果及外部副作用观察。
6. 将执行结果反馈给模型，并维护 Activity、Gate、预算、取消与异常状态。
7. 由 Hub 检查待提交改动与本地测试，通过后经获准能力完成提交推送，查看目标版本的 CI 结果；失败则在原意图、预算和授权内修复。
8. 依据已确认 Intent 对照实际交付与派生 Issue，组织版本明确的 Evidence 和 PR / Review 影响、结果说明，交由用户介入实际运行并作最终验收。

越权、授权失效或能力验证条件失效时，受影响操作不得继续；重要变化交由人工裁决。中断或结果不明时，先核查副作用和恢复条件，不假定回滚、成功或可安全重试。正式规则分别见[治理](governance.md)和[安全](security.md)。

## Session、Run 与 Activity

需要分开这些概念，才能让会话重建不改变授权和工作事实。

- **Session** 是可重建的运行上下文，不是正式授权与审批的权威来源。
- **Run** 是有边界、有预算、可追溯的一次实际执行。首版只允许一个主要写入 Run。
- **Activity** 是 AIDLC 活动单位。Run 可在有效授权下跨多个 Activity；Activity 不等于 Issue，也不等于 Run。

本次不设计完整 AIDLC 阶段模板、运行状态枚举或调度系统。对象语义、重要变化与人工 Gate 见[治理文档](governance.md)。

## 事实、交付与未来 Runtime

目标与预期行为以用户已确认的 Intent 为唯一规范依据；Intent 及其他正式领域记录由 Hub Protected Records 保护。代码及 Commit 以 Local Git 为准；真实执行与副作用以 Tool Execution Observations 为观察来源；远程交付发生时以 Remote GitHub 为准。它们之间的协调和恢复见[权威事实源](governance.md#权威事实源与持久化边界)。

当前交付目标、待确认的 MVP 边界与延期范围以[验证文档](validation.md)为准。未来可扩展 Codex App Server、MCP Client / Server，但必须遵守同一 Hub 治理契约，包括授权检查、受控执行、预算、Gate、Evidence 与恢复。

首版不实现完整 Codex Runtime 或 MCP Client / Server。MCP 提供互操作协议，不提供权限证明；本文件不定义未来适配 API 或具体技术选型。
