# 产品架构与 Runtime 职责

本文件说明已确认的产品职责关系、TypeScript 目录组织与后续设计方向。当前已有正式 JSON 项目看板及保留的 B1–B3 SQLite / HTTP / CLI；目录约定不是运行时隔离证明，当前最小 Harness 仅使用脚本化替身，后续模型 / 执行设计不表示已有能力。实现与验证状态以[工程状态](project-status.md)为准，领域对象以[治理](governance.md)为准。

## 最小 Harness 实现（2026-10-26）

domain/harness.ts 定义候选、模型端口及端点/负载计量声明（`providerKind`、`endpoint`、`measureStepInputBytes`）、输入快照、运行时绑定快照（`ModelRuntimeBinding`）、逐请求字节预算与 Run。harness/context.ts 只投影当前意图、一个需求、同需求子产物聚焦大纲（`focusOutline`）及适用长期信息和最小出处；必要内容超预算停止，可选信息省略可回查。harness/loop.ts 组织有界多步 ReAct 工具循环与单步回退，按每次真实模型请求计量调用次数与实际外发 UTF-8 负载字节（涵盖快照、历史 `turns` 工具输出及工具 Schema，明确区分 UTF-8 字节预算与 LLM 分词器 Token 估算），在恢复时仅累计新执行的工具调用，并在中途失败时保留已发生的消耗计量。infrastructure/scripted-model.ts 是显式声明 `local://in-memory` 的确定性本地替身，infrastructure/providers/ 提供高层供应商抽象与 `RuntimeRegistry` 统一解析。

application/HarnessService 经人端启动产生明确项目 / 需求范围，统一在 `start`、`resume`、`fork` 和 `execute` 使用同一 `ResolvedRuntime` 核查外发边界（`egressScope`）与运行时配置版本（`configVersion`），并为每次执行尝试生成独立 `executionId` 阻断超时或取消后的迟到回调污染。恢复、会话内模型切换与分叉均遵循“先完成全部修订、授权、运行时、外发及剩余预算前置检查，再原子写入 Run”的顺序：检查失败不清空既有候选、不改动模型绑定或步骤账本；项目修订变化后分叉默认拒绝直接继承旧步骤观察（`STALE_OBSERVATIONS_NOT_INHERITABLE`）；切换至仅支持 `propose` 的模型时完整保留已执行工具调用及输出（不静默截断为 200 字符）并纳入输入字节预算核查。

domain/record-candidate-mutations.ts 提供共享的纯领域语义比较与级联失效计算，供人端普通编辑（`RecordProjectService.previewEdit` / `saveRecord`）与模型候选初检、预览（`HarnessService.preview`）、正式应用（`RecordProjectService.applyRunCandidate`）复用：纯键顺序或无序集合顺序调整不误撤销核查与整体接受，真实工作内容或验收条件修改统一将受影响核查置为 `unknown`、沿 `dependsOn` 级联回退下游已完成对象、撤销父 Requirement 整体接受并保留原证据、来源引用与完整审计前值，同时严格隔离人端与模型的权限入口。Run 与正式项目通过 JsonRunStore / JsonRecordProjectStore 分存，当前为单进程应用恢复机制，不声称跨存储事务或 OS 防篡改。

需求详情的 RunPanel 展示持久化的运行时绑定（ID、配置版本、供应商、模型、端点、外发属性）、UTF-8 字节预算账本、公开步骤账本及包含真实 `effects` / `warnings` 的候选保存预览，复用既有通知并补读。Run 不自动改变 Requirement 工作状态，服务重启不自动重发中断调用。操作及限额见[Harness 指南](harness-quickstart.md)。

## 跨会话冷启动恢复与聚焦投影（2026-10-27）

落实 AIDLC 第 4 章《内存库标准》（`book/chapters/ch04-memory-bank-standards.md`）中的“最小可恢复上下文栈”与“冷启动恢复 A/B 检查”原则，采用用户确认的方案 A（纯聚焦恢复投影，零 Schema 扩张）：

1. **领域投影与状态机（`domain/recovery.ts`）**：
   - `buildRecoveryProjection`：纯函数接收当前正式 `RecordProject` 与可选最新运行记录 `HarnessRun`，纯只读计算冷启动上下文，提炼 Intent、当前 Requirement 拆解进度、最新 Run 状态、未决候选、当前生效授权与运行时绑定、来源依据与未决假设。
   - `deriveNextSafeAction`：确定性状态机，回答 AIDLC 第 4 章的 7 个核心问题（目标、进度、下一步安全动作、为何可做、适用修订与授权、证据与理由、未知项与人工 Gate）。
   - **缺口停止机制（Fail-Closed）**：当发现记录矛盾（如需求声明为 `done` 但关联核查为 `unknown` 或缺少 passing 证据）、项目修订推进导致 Run 基准滞后（`project.revision !== run.baseRevision`）或意图未人工确认（`proposed` 状态）时，坚决返回 `STOP_AND_REPORT_GAP`、`RECONCILE_STALE_RUN` 或 `REQUIRE_HUMAN_INTENT_CONFIRMATION`，严禁模型自主猜测或盲目执行。
2. **应用服务与导出接口（`application/recovery-service.ts`）**：
   - `RecoveryService` 提供 `getRecoveryView`（结构化只读视图）与 `formatRecoveryMarkdown`（Markdown 纯文本报告），并注入 `RecordStructureValidator` 执行实时结构完整性核查，发现损坏或非法结构时推导 `STOP_AND_REPORT_GAP`；
   - 在 HTTP 服务（`src/infrastructure/http-server.ts`）暴露只读路由 `GET /api/record-projects/:id/recovery`（支持 JSON 与 `?format=markdown`），采用先校验生成后发送响应头的防御策略，杜绝 `ERR_HTTP_HEADERS_SENT` 异常；
   - 提供独立子进程消费者入口脚本（`src/presentation/recovery-cli-consumer.ts`），支持跨会话外部程序在 OS 原生进程隔离下运行并回答 7 大核心问题，详见[冷启动简报](templates/cold-start-acceptance-brief.md)。

## 正式 JSON 项目与看板投影

SQLite 保留账户、工具范围与旧来源；每个旧正式 Issue 只预览为一个 Requirement 草案，不推断分层或新接受。人端确认后新 JSON 成为该项目正式内容，BoardService 拒绝旧业务写入，仍允许撤销令牌，避免两套可写事实源。旧批准与父子保留来源，意图新表示另待核对。操作和限制见[指南](record-board-quickstart.md)，应用接口不证明宿主防篡改隔离。

## 为什么需要 Hub 控制层

开发者需要在 Agent 推进前理解方案的理由、收益和风险，并在推进后核对实际结果与原始意图。理解速度落后于执行、Issue 描述与实现发生语义偏移，都会使规范的记录无法支持真实判断。

Hub 因此把任务看板、方案决策和实际执行连接起来：以问题边界组织交付单元，在有效授权内执行，收集真实观察，并让 Issue 中的预期与 PR / Review 中的结果保持对应。Agent 不能仅凭自身判断建立授权、证明真实执行或确认最终交付。

产品交互从用户的想法或已有 Intent 开始，经对话明确意图、责任、边界与验证方式，由用户确认；已有且适用的确认可复用。正式执行入口仍是通过准入的 Issue 和人工批准的有效 Grant；出口是可追溯的实际工作、Evidence 与绑定交付版本的 Review。人工最终验收独立于 Run 完成。对话出口、领域关系和交付说明的具体语义见[治理](governance.md#对话前置与意图确认)，交付门禁见[验证](validation.md)。

本阶段可用角色走读和明确标注的示例检查信息是否足够，不声称工具、CI 或真实项目已运行。首版候选优先覆盖既有的云端模型、自有 Harness、单主要写入 Run 和上述闭环；本地辅助模型、已有 Agent 适配及更广的平台能力按既定优先级后置。具体实现依赖仍须技术验证与实现准入。

| C04 | 在有效 Grant 与已验证能力范围内运行自有云端 Harness，保持单主要写入 Run | 看板记录不能控制实际运行；D1.2 / D4.3 / D6.4 | 用户能了解执行范围、预算、停止条件，越界动作不会被放行 |
| C05 | 呈现真实动作、结果、证据和异常，区分模型建议与已发生事实 | 完成声明不能证明执行；D2.3 / D3.3 | 当前工作、等待原因、失败、部分结果和未知项可查 |
| C06 | 提交前检查影响与本地测试，获准提交推送并读取目标版本 CI，准备交付说明 | 文本与交付不一致；D6.2 / D6.9 | What / Why / Impact / Result 对应具体版本；失败返工后重新检查 |
| C07 | 用户实际运行，对照 Intent、Issue / PR 影响说明作最终验收 | CI 不能单独发现语义偏移；D6.5 / D6.9 | 接受或退回有场景、环境、版本和人工依据 |
| C08 | 授权失效、取消、中断或结果不明时停止依赖未知结果的推进，并核查恢复条件 | 停止与记录缺失不能证明无副作用；D3.4 / D4.6 | 能区分请求停止、实际停止及未核查副作用；旧授权不会自动恢复 |

云端优先、人工责任及单主要写入 Run 属于既有确认；B1 看板已采用下述本地 Web / SQLite 工程基线，云端供应商、Runtime 存储与隔离实现仍未确定。此前 DeepSeek Loop 作为技术起点，不代表当前已接入模型。

用户同时确认：看板版本先在 Codex 等外部 Agent 中进行反向对话，在 Hub 中记录方案、取舍和用户决定。这里指外部讨论后的记录流程，不是 Hub 正式适配 Codex CLI，也不授予外部 Agent 绕过 Hub 的执行权限；看板版本不要求内置模型或工具执行。

| 看板版本需要承载的内容 | 已确认的用户价值 | 最小交互建议，尚未作为最终布局确认 |
| --- | --- | --- |
| 项目内 Intent / Issue 概览及关联 | 清楚当前要做什么、解决什么问题，能回到最初意图 | 从项目概览查看 Intent 与关联 Issue；Issue 显示目标、边界与预期结果 |

| 验证方式与意图对应关系 | 推进前知道如何判断产出符合原始意图 | 在 Issue 中记录验证场景、预期结果和对应 Intent；实际未验证时明确标识 |

建议最小操作为记录 / 查看 Intent 与 Issue 的关联，维护方案及其决定依据，维护验证计划。用户进一步确认采用类似 Multica 的工具写入交互：提供 CLI 或其他形式工具完成写入，由用户检查与审批；已明确关键内容需审批，普通记录可在用户划定边界内直接保存；B1 已实现按项目 / Intent 绑定的读取和新增提案范围、HTTP 服务及 CLI，具体基线见下节；B2 已实现普通记录及更完整概览，B3 已实现候选关键修订与差异审查，B2 记录和详情两部分已获用户试用确认。工具写入与正式确认的边界见[治理](governance.md#工具写入与人工检查)。工具或用户录入的进度、对话结论或证据与系统实际执行观察分别标明来源；没有 Runtime 时不显示工具运行、CI 或自动交付已完成。

```text
项目概览
Intent：要解决的问题、预期结果、确认与修订信息
关联 Issue：交付单元、当前计划状态、待用户决定事项

Issue 详情
做什么：问题、范围、关联 Intent、预期结果
为什么：备选方案、收益 / 风险、外部反向对话结论、用户决定
如何验证：场景、预期、对应意图；实际结果 / 证据在发生后补充
```

新增交付单元的交互已确认采用[待审变更](governance.md#新增交付单元与变更审查)：工具提交建议，用户查看变动内容与理由，确认后才纳入正式计划和相应工作范围。建议看板将“待审建议”与正式 Issue 清单区分；具体页面布局仍是候选。

待审建议的文字线框如下，是依据已确认规则提出的交互草案，不代表已实现的审批界面：

```text
待审建议：新增交付 Issue
关联 Intent / 原交付清单及所基于的版本
变动前：当前正式计划
变动后：拟新增的工作及受影响内容
为什么变动：发现依据、必要性、收益与风险
如何验证：新增工作的预期结果与验证方式

[确认本次变更]  [退回补充]  [拒绝]
```

未确认时保留原正式计划。确认针对界面实际展示的建议及版本，不允许审批后替换成另一份内容；具体冲突处理和保护机制仍待实现验证。

后续 Runtime 工作区继续使用下节草案，并在接入实际能力后呈现执行、检查与交付；看板可用不证明 C04–C08 的执行能力成立。PR 采用[四段式交付说明](governance.md#pr-四段式说明与人工证据)；PR 文本结构已确认，但由谁创建、何时创建和具体上传入口尚未决定，不作为先行看板交付的阻塞项。

## 最小工作区交互候选

本节保留面向后续 Runtime 的 P1-2 低保真建议，尚未获布局确认，不是先行看板的全部必做范围。建议把六类信息区域组织到同一工作区，用事项列表 / 看板连接当前交付单元的三个视图：**对话与方案、执行、交付与验收**。适用 Intent 摘要和确认状态常驻，详细内容按需展开；用户切换视图时保留当前 Intent 与 Issue。它是信息组织建议，不指定页面数量、前端框架或最终视觉布局。

收益是减少跨工具重建上下文；风险是单一工作区信息过密。因此默认突出当前问题、当前动作和需要用户判断的事项，日志和历史放在展开区。状态用文字及其他提示共同表达，关键操作支持键盘；小窗口的具体布局与完整可访问性验证留给实现阶段。

```text
工作区 / 项目
适用 Intent：摘要、确认状态、修订标识       [查看原意图 / 修订差异]

事项列表或看板                         当前交付单元
父 Intent 与子 Issue 关系              [对话与方案] [执行] [交付与验收]
本单元预期结果                         当前问题、实际进展、下一步及其依据
                                       需要用户判断的事项 / 可展开证据
```

| 视图 | 默认可见信息 | 主要操作与出口 | 不满足条件时 |
| --- | --- | --- | --- |
| 对话与方案：C01–C03 | 已确认上下文、候选意图、问题缺口；单元边界、方案理由、收益风险与预期证据 | 补充 / 纠正草案；确认 Intent；理解交付方案后查看执行授权 | 关键歧义未解决或 Intent 未确认时留在澄清，不由模型自认确认 |
| 执行：C04 / C05 / C08 | 适用意图和授权范围、预算、当前动作、真实观察、等待原因、失败或未知 | 用户明确授权后开始；请求暂停 / 取消；查看异常与恢复依据 | 授权或能力不足则不开始受影响动作；停止请求与已停止分开展示 |
| 交付与验收：C06 / C07 | 版本、差异、影响、本地检查、CI、PR / Review 材料、场景与证据缺口 | 查看证据；用户记录实际运行观察后接受 / 退回；需要改意图时发起讨论 | 本地失败先修复，CI 失败在适用授权内返工，实际偏差退回，不自动改目标 |

关键衔接按以下方式表达，正式含义继续以[治理](governance.md)为准：

1. **草案 → 已确认 Intent：** 展示本次拟确认的目标、边界、责任及验证方式。用户可纠正或暂不确认；单次点击不能顺带授予全部执行权限。
2. **已确认 Intent → 可执行单元：** 每个 Issue 解释它解决的独立问题和方案依据。若一个单元足以独立交付，不为展示父子层级继续拆分。
3. **理解方案 → 执行：** 分开展示拟执行的路径 / 工具范围、预算、停止条件和验收条件，由用户批准 Grant。已批准范围内的普通实施不增加逐步审批。
4. **执行 → 交付：** 从真实观察组织材料；本地适用检查失败或未知时，不能显示为已具备提交条件。提交、推送、PR 和 CI 分别记录事实，避免一个“完成”覆盖全部结果。
5. **交付 → 人工验收：** 预期结果和实际结果并列，显示证据适用版本。用户记录实际运行环境、场景、观察及决定；Run 结束和 CI 通过均不自动接受。
6. **意图修改：** 展示修改前后、理由和受影响 Issue / Grant / Evidence；先讨论并取得明确授权，再更新适用范围。受影响执行须重新评估，不能以修改文字掩盖偏差。

显示词如“草案”“等待判断”“观察失败”“副作用未核查”只是信息表达，不是本轮冻结的状态机。无数据、正在获取、读取失败、部分结果和旧版本结果分别说明；保存失败保留用户输入并明确未生效，不显示已确认。重复确认 / 验收请求不得产生重复正式记录，冲突或过期视图要求核对适用版本；具体一致性和保护机制在技术阶段验证。

## 贯穿示例：标题筛选修复

以下均为**虚构设计示例**，不构成真实需求、正式 Intent / Grant、Git 记录、CI 结果或人工验收。

示例意图：按标题关键词筛选事项；关键词清空后恢复全部；不修改原始事项内容。用“修复登录异常（未完成）”“登录页增加提示（已完成）”“补充文档（未完成）”三条数据说明：“登录”应命中前两条，空关键词应显示三条。大小写、空白等未涉及的细则不由此推导为 AgentHub 的产品需求。

| 位置 | 示例中呈现的内容与预期处理 |
| --- | --- |
| 对话与方案 | 澄清筛选依据，展示“修改显示条件，保留原始数据”的方案；说明误过滤已完成事项的风险 |
| Intent 与 Issue | 故事中假设用户确认示例意图；一个“修复标题筛选与清空恢复”的 Issue 足以独立交付，输入处理和列表更新不再拆成操作型子 Issue |
| 执行 | 假设另行批准有限范围的 Grant，先检查 / 复现，再修改和验证；界面显示真实结果，故事假设不产生当前工具权限 |
| 交付 | 对照示例意图列出改动、理由、影响、检查与未知项；“示例版本 A / B”仅为故事标识，不冒充真实 Commit |
| 语义偏移 | 若实现额外只显示未完成事项，即使现有 CI 通过，人工输入“登录”仅看到第一条，也应判定与意图不符 |
| 修复与再验收 | 维持原意图修复，对新版本重新检查与人工核对；旧版本证据不能直接成为新版本验收依据 |

看板分单元推进见[编码计划](board-implementation-plan.md)。B1 已采用 React / Vite、SQLite 和本地服务实现贯穿闭环，其当前工程事实见下节；工程选择不替代已确认领域规则，也不证明完整看板或 Runtime 已完成。

## TypeScript 工程组织

2026-10-23 先建立单包 Node.js + TypeScript / ESM 骨架，随后用户基于编码计划明确要求开始编写代码。B1 继续单包组织，采用 React 19.3.1 / Vite 8.3.5、本地 Node HTTP 服务、better-sqlite3 13.0.3 和原生 parseArgs CLI；精确版本以 package.json / 锁文件为准。开发入口使用 tsx 解析源码的 ESM 导入，正式 Node 产物由 tsc 编译；浏览器有单独的 JSX / DOM 类型检查。这些是本轮实现基线，不是最终平台、安全选型或用户整体验收。

| 路径 | 后续代码职责 | 依赖与边界 |
| --- | --- | --- |
| src/index.ts | 组合 SQLite、用例、认证与 HTTP 服务并启动 | 不在此堆积领域规则、自动模型调用或工具执行 |

## 看板自动更新实现

B1 当前采用浏览器原生 EventSource / SSE 接收服务端变更提示，再调用原有鉴权快照接口；不新增运行依赖或数据库结构。HTTP 适配在用例事务成功返回后通知，人端只收到空通知；未登录或工具身份不能订阅。会话在通知 / 心跳时复查，退出、断开和服务停止均释放连接。机制依据 [MDN SSE 说明](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)及 [Node 24 HTTP API](https://nodejs.org/docs/latest-v24.x/api/http.html)，本机结果见状态文档。

前端合并连续读取，断线重连、恢复网络、返回页面会补读；临时读取错误另行重试。列表更新不重挂载当前输入组件，审阅另保留所审版本，正式计划变化后需用户重新核对；同步不能静默把原决定绑定到新版本。当前只通知经本服务入口写入的变化，不监控绕过服务的数据库修改；不因页面更新推断执行或验收。

## 三种运行模式与优先级

为兼顾运行过程的掌控与不同模型来源，产品规划三种模式。它们是目标，不代表已有适配或已验证能力。

| 模式 | Hub 的职责 | 优先级与待验证边界 |
| --- | --- | --- |
| 云端模型 + Hub 自有 Harness | 由 Hub 组织上下文、调用模型、检查执行条件并反馈工具结果 | 第一版优先；既有 DeepSeek Loop 为技术起点，本轮未重新指定模型或服务商 |
| 本地模型 + Hub 自有 Harness | 使用同一治理语义组织本地推理及结果使用 | 后续可先承担小型 Reviewer 或文档总结，考虑本机算力限制；不替代人工最终验收 |
| 已有 Agent + Hub 约束 | 组织任务、观察执行，并通过实际可用的接口施加约束 | 后续方向；需证明跨 Agent 操作是否能绕过 Hub，不把看板记录等同于运行时控制 |

自有 Harness 允许 Hub 直接设计运行循环，其安全效果仍须真实验证。接入不同模式时，应说明实际可见、可控和不可控的部分；当前已有本地 Web 看板工程基线，未确定模型适配 API、最终产品平台或调度机制。

## 职责与信任边界

下列名称表示架构职责，不代表已有同名实现文件或进程。

| 角色或组件 | 承担的责任 | 必须遵守的边界 |
| --- | --- | --- |
| 人 | 理解方案的理由、收益和风险；商讨并授权意图修改；批准任务授权、可信晋升并介入最终实际运行验收 | 不将模型完成声明视为人工裁决 |
| Hub 控制层 | 以已确认 Intent 对齐 Issue、方案与交付事实，组织提交前检查、提交推送、CI 反馈及人工验收材料，维护授权、预算与恢复 | 正式记录和秘密不能暴露给 Agent 任意写入 |
| DeepSeek Agent Loop | 首版由 Hub 自有 Loop 组织上下文、模型调用、工具建议和结果反馈 | 模型输出只是建议；每次实际执行受当前授权和能力约束 |
| Agent | 分析任务、提出操作并推进获准工作 | 执行进程不可信，不能控制授权或可信组件晋升 |
| Tool Executor | 将获准操作转化为真实执行，收集结果和副作用观察 | 负责执行控制，不能将建议直接视为许可；底层机制须验证 |
| Sandbox | 候选的受限进程执行边界 | 机制安全性和适用环境待 X1 证明，名称不代表安全 |
| Trusted Git Broker | 受限修改 Git 管理状态并完成获准本地 Commit | 不提供任意高权限 Git 命令转发，候选实现须经验证和晋升 |

Agent 可以直接修改授权工作文件；Git 管理状态的受限修改和本地 Commit 交由可信 Git Broker。具体保护要求见[安全文档](security.md)，不在本文件预选具体进程拆分或存储实现。

## Hub 自有 DeepSeek Loop

为使自主执行始终处于有效授权内，Hub 应完成以下闭环：

1. 读取用户已确认的 Intent 及其适用修改记录、派生 Issue、已确认方案、有效 Grant 和 Run 状态，确定交付单元、Activity、预算与可用能力；方案、收益和风险尚需人工判断时先呈现，不能由模型自行改写 Intent。
2. 组装包含适用 Intent、责任、约束、决策依据与真实观察的上下文，区分可信领域事实与不可信指令、项目内容和工具返回；摘要不替代正式确认或授权。
3. 调用模型，接收分析与工具操作建议。
4. 在实际执行前检查当前 Grant、能力准入和执行环境；建议本身不授予权限。
5. 通过受控执行能力完成获准操作，收集真实结果及外部副作用观察。
6. 将执行结果反馈给模型，并维护 Activity、Gate、预算、取消与异常状态。
7. 由 Hub 检查待提交改动与本地测试，通过后经获准能力完成提交推送，查看目标版本的 CI 结果；失败则在原意图、预算和授权内修复。
8. 依据已确认 Intent 对照实际交付与派生 Issue，组织版本明确的 Evidence 和 PR / Review 影响、结果说明，交由用户介入实际运行并作最终验收。

越权、授权失效或能力验证条件失效时，受影响操作不得继续；重要变化交由人工裁决。中断或结果不明时，先核查副作用和恢复条件，不假定回滚、成功或可安全重试。正式规则分别见[治理](governance.md)和[安全](security.md)。

## Session、Run 与 Activity

需要分开这些概念，才能让会话重建不改变授权和工作事实。

- **Session** 是可重建的运行上下文，不是正式授权与审批的权威来源。
- **Run** 是有边界、有预算、可追溯的一次实际执行。首版只允许一个主要写入 Run。
- **Activity** 是 AIDLC 活动单位。Run 可在有效授权下跨多个 Activity；Activity 不等于 Issue，也不等于 Run。

本次不设计完整 AIDLC 阶段模板、运行状态枚举或调度系统。对象语义、重要变化与人工 Gate 见[治理文档](governance.md)。

## 事实、交付与未来 Runtime

目标与预期行为以用户已确认的 Intent 为唯一规范依据；Intent 及其他正式领域记录由 Hub Protected Records 保护。代码及 Commit 以 Local Git 为准；真实执行与副作用以 Tool Execution Observations 为观察来源；远程交付发生时以 Remote GitHub 为准。它们之间的协调和恢复见[权威事实源](governance.md#权威事实源与持久化边界)。

当前交付目标、待确认的 MVP 边界与延期范围以[验证文档](validation.md)为准。未来可扩展 Codex App Server、MCP Client / Server，但必须遵守同一 Hub 治理契约，包括授权检查、受控执行、预算、Gate、Evidence 与恢复。

首版不实现完整 Codex Runtime 或 MCP Client / Server。MCP 提供互操作协议，不提供权限证明；本文件不定义未来适配 API 或具体技术选型。

## B2 概览与记录实现

B2 沿用现有技术栈和 SSE 通知，未添加依赖。概览连接原 Intent、正式交付单元与近期记录；Issue 详情从已批准提案和人端决定读取做什么、为什么、方案收益风险和验证计划，展示父子关联；待审建议保留在原提案区域。讨论和报告不生成执行、CI 或验收状态。

domain 定义记录及对象 / 类型边界，application 检查范围、关联和 Intent 版本，事务追加内容与幂等回执；infrastructure 提供记录存储与鉴权 HTTP。SQLite user_version 从 1 增至 2，事务增加 records 表与项目索引，不改写旧账户或业务记录；比已知版本更高的库拒绝打开。迁移测试使用临时旧库，不声称已升级用户数据。

CLI 新增 scope（GET /api/access，仅读取当前认证身份及自身工具边界）与 record（POST /api/projects/:id/records）；overview 仍经鉴权快照读取。CLI 不直接写库，服务成功提交后再发送空变更提示。工具自身查询不返回令牌或其他工具范围。

界面将内容展示、Issue 追溯、记录与范围选择拆为 details.tsx、issues.tsx、records.tsx、tool-scope.tsx；草稿按关联对象保存在页面内存中，同步和视图切换保留，刷新 / 退出清除。已保存记录按原文显示，外部来源为普通文本，不执行其内容。当前快照一次读取项目全部记录，尚未实现分页；本地演示规模以外的性能未验证。

## B3 修订通路实现

domain/changes.ts 定义精确变更范围、Intent / Issue 候选及原快照和授权记录。BoardService 复用原人端 / 工具身份和事务幂等框架，检查对象版本、Intent 版本、计划版本及父子关系无循环；关键建议和普通记录采用不同入口。候选 after 完整保存，before 由服务生成；状态变更保留其中的内容。

SQLite v3 新增 changes 表，保存候选、原 / 新内容、人端商讨授权及撤销历史、最终决定；Issue 增加 version 与确认时 intentVersion。旧库事务补齐 Issue 元数据，已有业务文本和请求回执保留。应用 Issue / Intent 修订、候选决定和计划版本与回执同事务提交；记录本身不增加计划版本。

CLI change 对应 POST /api/projects/:id/changes；人端通过 changes/:id/authorization、revoke-authorization、decisions 分别登记、撤销和决定。普通工具没有这些人端能力。界面 changes.tsx 提供差异审查和版本保护；Issue 详情连接修订历史，并提示旧 Intent 对应关系待核对。SSE 继续只发空通知，事实经鉴权快照补读。

当前没有自动重基候选、批量改写派生 Issue、原地编辑提案或自动范围继承。需要调整时回到明确的新候选和人端判断。界面侧栏新增滚动，支持项目列表超出窗口后的访问。
